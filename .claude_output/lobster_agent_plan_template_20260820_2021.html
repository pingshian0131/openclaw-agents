怎麼用這份模板

先想清楚「這隻龍蝦是誰、每天做什麼」，再決定它需要哪些檔案、技能、排程與記憶
說明流程
填空 → 產生 workspace先目的後工具一次一隻龍蝦

「龍蝦」＝一隻 OpenClaw Agent。一隻龍蝦不是一段 prompt，而是一個 workspace 目錄：一組 Markdown 檔案（人格、規則、環境）＋ 一批 Skills（可重複的工作流程）＋ 一批 Cron Jobs（不用人開口就會發生的事）＋ 一套 Memory 規則（什麼該記、什麼不准記）。這份計畫書的目的，是讓你在動手建目錄之前先把這四件事講清楚。

填寫順序不要跳：Part 1（目的）與 Part 2（日常）決定後面全部。很多人一開始就在挑工具，結果做出一隻「什麼都能做、但沒有任何一件事是它負責」的龍蝦。

📝 建議的填寫節奏
workflow 
Step 1  封面 + Part 1 目的      → 一句話講完它為什麼存在（含「它不做什麼」）
Step 2  Part 2 日常             → 畫出一天／一週的節奏：誰觸發、做什麼、交付到哪
Step 3  Part 3 檔案地圖         → 把 Part 1-2 的內容拆進 6 個 .md 檔案
Step 4  Part 4 Skills           → 日常裡「重複三次以上」的流程，才值得變成 Skill
Step 5  Part 5 Cron Jobs        → 日常裡「不需要人開口」的部分，才值得變成排程
Step 6  Part 6 Memory           → 決定哪些事跨 session 要記得、哪些永遠不准寫下來
Step 7  Part 8 紅線             → 寫下「這隻龍蝦絕對不能自己決定」的事
Step 8  交付檢查清單            → 逐項打勾，才算計畫書完成
ℹ️ 本模板的填空標記：畫底線的 ＿＿＿ 是你要填的；❓ 開頭的引導問題是幫你想的，不用寫進最終檔案；可複製的程式碼區塊則是直接貼進 workspace 檔案的骨架。
⚠️ 一份計畫書只寫一隻龍蝦。如果你發現自己在同一份計畫書裡寫「它也要處理人事、也要顧品管」，那是兩隻龍蝦，請拆成兩份 — 邊界模糊的 Agent 在權限與記憶上最容易出事。

封面 · 命名你的龍蝦

名字就是它的職責範圍宣告 — 取不出名字，通常代表目的還沒想清楚
必填身分
職能命名一句話定義emoji
＿＿＿＿＿ 龍蝦計畫書
提案人：＿＿＿ 日期：＿＿＿ 版本：v0.1

一句話定義：這隻龍蝦是 ＿＿＿＿＿，負責替 ＿＿＿ 完成 ＿＿＿＿＿，並在 ＿＿＿ 之前主動提醒。

  • 名字怎麼取？建議「職能 + agent」而不是人名或代號 — hr-agent、qc-agent、mc-agent 這種名字一看就知道邊界在哪；小龍、lobster-01 則什麼資訊都沒給。
  • 如果只能保留一項職責，你會保留哪一項？那一項就是它的名字。
  • 誰會叫它？是一個人、一個部門、還是另一隻龍蝦（子代理／跨 Agent 協作）？
  • 它的語氣應該像顧問、像稽核、還是像值班同事？這會直接寫進 SOUL.md。
🪪 封面欄位（先填這些，再往下走）
龍蝦名稱（workspace 目錄名）：例 hr-agent　→ 生物設定 Creature（它自認是什麼角色）：例 人力資源營運助理　→ 主題 Theme（服務的領域 / 場景）：例 台灣冷凍粉圓食品工廠　→ 語氣 Vibe（三到四個形容詞）：例 謹慎、清楚、以證據為準　→ Emoji：例 👥　→
ℹ️ 這五欄之後會原封不動變成 IDENTITY.md，所以現在填的字就是最終稿，不要寫「待討論」。

Part 1 · 龍蝦的目的

為什麼要有它、它取代了哪個人力動作、以及它明確「不做」什麼
必填定位
存在理由職責範圍非目標成功指標

目的段落最常見的失敗是只寫「做什麼」不寫「不做什麼」。範圍外的事沒寫下來，Agent 就會在別人問到的時候硬答 — 這是後續所有幻覺與越權的起點。「不做什麼」的字數應該和「做什麼」差不多。

✅ 目的四段式（直接填，這段之後會進 AGENTS.md 的「職責」節）
① 痛點：現在這件事由誰做、要花多久、常出什麼錯？→ ② 職責範圍（3–5 條，用動詞開頭）：→ ③ 明確不做（3–5 條，含「不做決定」與「不碰的資料」）：→ ④ 成功指標（怎麼判斷它有用，要可量測）：→
  • 權威資料來源是誰？Agent 的結論以哪個系統的紀錄為準（API／資料庫／某份文件）？聊天內容不能當正式紀錄。
  • 它是「查詢型」還是「會寫入」？如果會寫入，寫入的是草稿還是正式資料？
  • 沒有它的時候，這件事會怎麼被漏掉？寫不出來，代表這隻龍蝦可能不必存在。
  • 成功指標可以是：提醒命中率、人工回工次數、平均處理時間、漏單數量 — 不要寫「讓大家更方便」。
🔧 範例（可對照本 repo 的 hr-agent）
purpose.md 
① 痛點
   排班與加班核准散在 Excel 與 LINE 群，週六加班常在事後才發現沒送審，
   而且無法即時知道當班人員是否具備該產線的作業資格。

② 職責範圍
   - 查詢工作曆、輪班與產線人力配置
   - 核對平日夜間／週六加班的申請、核准狀態與實際工時
   - 追蹤出勤、缺勤、休假與補休餘額
   - 檢查員工訓練、證照與產線作業資格
   - 指出排班、人力、資格與工時風險並提出建議

③ 明確不做
   - 不核准加班、請假、排班或資格異動（一律人工核准）
   - 不修改薪資、津貼與出勤結算
   - 不直連資料庫、不繞過權限
   - 不輸出身分證號、帳戶、住址、健康資料與完整薪資明細

④ 成功指標
   - 週六加班「事後才發現未送審」件數：每月 3 件 → 0 件
   - 排班資格缺口在上班前 24 小時被指出的比例 ≥ 90%
⚠️ 「不做什麼」要寫成可執行的規則，不是願望。「不越權」是願望；「不核准自己建立的申請」才是規則 — 後者可以寫進 AGENTS.md 並被檢查。

Part 2 · 龍蝦的日常

它一天／一週實際上會被什麼觸發、做哪些動作、把結果交到哪裡
必填節奏
觸發來源日常動作交付管道升級路徑

「日常」是整份計畫書的轉軸：填完這格，你就同時知道哪些要變成 Skill（重複的流程）、哪些要變成 Cron（不需人開口的流程）、哪些要進 Memory（跨天必須記得的事）。先寫日常，後面三個 Part 幾乎是抄過去。

🕒 日常時間軸（填掉你會用到的列，用不到就刪）
daily-loop.md 
| 時機          | 觸發來源           | 龍蝦做什麼                | 產出交到哪         | 要記住嗎 |
|---------------|--------------------|---------------------------|--------------------|----------|
| 每天 08:30    | cron（排程）       | ___                       | Slack #___         | 日誌     |
| 每天上班中    | 使用者提問         | ___                       | 對話回覆           | 不需要   |
| 每週一 09:00  | cron（排程）       | ___                       | ___                | 長期記憶 |
| 每月初        | cron（排程）       | ___                       | ___                | 長期記憶 |
| 隨時          | 另一隻 Agent 詢問  | ___（只回彙整結論）       | 對話回覆           | 不需要   |
| 例外          | 發現異常／權限不足 | 停止並回報下一位核准者    | ___                | 日誌     |
  • 誰是觸發者？每一列都必須有明確觸發來源：人問、排程到點、webhook、或另一隻 Agent。沒有觸發來源的動作永遠不會發生。
  • 產出去哪？對話回覆、Slack／Telegram 頻道、webhook、還是只寫進 daily memory？「產生報告但沒人看」是最常見的浪費。
  • 哪一列會重複超過三次？那一列是 Part 4 的 Skill 候選。
  • 哪一列不需要人開口？那一列是 Part 5 的 Cron 候選。
  • 做不到的時候怎麼辦？API 回傳權限不足、狀態衝突、資料缺漏時，是停下來回報，還是猜一個答案？（正確答案是前者，而且要寫進 AGENTS.md。）
ℹ️ 預設回覆格式也算日常。建議固定成：結論 → 依據 → 風險／缺口 → 建議下一步；涉及寫入時多一行「操作狀態（草稿／待核准／已執行）」。格式固定，使用者才能快速掃過。

Part 3 · Fundamentals 檔案地圖

六個必備 .md ＋ 兩個選配：哪一句話該寫進哪個檔案
必填架構
~/.openclaw/workspace每個 session 注入subagent 只拿 AGENTS.md

一隻龍蝦 = 一個 workspace 目錄（預設 ~/.openclaw/workspace，多 Agent 時各有自己的目錄）。新 session 的第一個 turn，OpenClaw 會把這些檔案的內容注入 system prompt。所以「檔案分工」不是美學問題，而是哪些規則在哪些情境下還在生效的問題。

📁 建議的目錄結構（照著建就好）
workspace/ 
___-agent/                 # ← 你的龍蝦名稱
├── AGENTS.md              # 作業規則：流程、權限、紅線、輸出格式（必要）
├── IDENTITY.md            # 身分名牌：名字、角色、語氣、emoji（必要）
├── SOUL.md                # 人格與邊界：它在意什麼、怎麼說話（必要）
├── USER.md                # 服務對象：誰在用、角色權限、語言時區（必要）
├── TOOLS.md               # 環境實況：可用 API、認證來源、使用限制（必要）
├── MEMORY.md              # 長期記憶：已確認背景、穩定決策、待確認（必要）
├── HEARTBEAT.md           # 定期巡檢指示（選配，預設可停用）
├── memory/
│   └── YYYY-MM-DD.md      # 每日工作日誌（當天事實、決策、待辦）
└── skills/
    └── ___/SKILL.md       # 這隻龍蝦專屬的技能
✅ 邊界表 — 「這句話該寫哪裡」
如果你想寫的是…寫進理由
硬規則、權限、禁止事項、輸出格式AGENTS.md每個 session 都注入，subagent session 也只注入 AGENTS.md — 想讓子代理也遵守的規則只能寫這裡
名字、角色、emoji、一句話定位IDENTITY.md最短的檔案，只放名牌資訊
語氣、在意什麼、怎麼拒絕SOUL.md人格層；要短 — 這段內容位於 prompt cache 邊界之上，頻繁改動會讓快取失效
使用者是誰、角色權限、語言時區USER.md每個 session 注入，且有獨立字元預算（約 4,000 字元），寫太多會被截斷
API base URL、token 來源、可呼叫的能力TOOLS.md環境說明；注意它不控制工具是否可用，只是給模型的指引
跨 session 要記得的穩定事實與決策MEMORY.md精煉層，不是原始逐字稿
今天發生什麼、誰決定了什麼memory/YYYY-MM-DD.md工作層，可被 memory_search 檢索，不會每輪注入
「每天早上自動檢查…」HEARTBEAT.md 或 cron job定期巡檢；只在 heartbeat 事件時讀取
可重複的多步驟工作流程skills/___/SKILL.md工具已經有了、但需要固定做法時用 Skill
⚠️ 不要把同一條規則抄進三個檔案。重複的規則在改版時只會被改到一份，剩下兩份變成互相矛盾的「舊法律」。規則的唯一家是 AGENTS.md。
ℹ️ Workspace 是預設工作目錄，不是強制沙箱。相對路徑從 workspace 解析，但除非另外啟用沙箱，絕對路徑仍可讀到系統其他位置 — 所以「不要把祕密放進 workspace」是規則，不是建議。

SOUL.md — 人格與邊界

它在意什麼、怎麼說話、什麼情況下會拒絕
必要人格
3–5 段就夠寫價值觀不寫流程改動會失效 prompt cache

SOUL 的作用是讓 Agent 在沒有明確規則可套的情況下，仍然做出你希望的選擇。所以這裡寫的是價值取捨（「寧可說不知道，也不要猜」），不是步驟。它應該短 — 這段內容在 prompt cache 邊界之上，每次改都會讓快取失效。

✅ 骨架（四段：使命 / 在意什麼 / 判斷準則 / 界線）
SOUL.md 
# Soul

你是 `___-agent`，使命是 ___（一句話，寫價值不寫功能）。

你關心的不只是 ___，還包括 ___、___ 以及 ___。
（把 Part 1 的「痛點」翻成它在意的事）

你以 ___ 系統中的已核定紀錄為準，會區分「申請 / 核准 / 實際發生 / 結算」，
不把推測包裝成事實。發現缺口時，先說明影響，再提出建議。

你保護 ___（使用者的什麼？隱私、時間、聲譽）。回答精簡、可追溯。
你不代替 ___ 做高風險決定，也不 ___。
  • 當資料不足時它該怎麼講話？「明確標示未查證」是可以寫進 SOUL 的行為傾向。
  • 它會為了看起來有用而多做嗎？如果不希望，就要明寫「不擴大範圍、不自行推論結論」。
  • 它保護誰？員工尊嚴、客戶隱私、還是老闆的決策時間？這句話會影響它每一次的措辭。

USER.md — 服務對象與角色權限

誰在跟它說話，以及那個人能看到什麼
必要權限
約 4,000 字元預算角色 ≠ 權限身分不明 → 降級

USER.md 最有價值的一段不是「使用者偏好」，而是角色關係表：同一個問題，員工問和主管問，能拿到的答案不一樣。另外務必寫下「無法確認呼叫者身分時怎麼辦」 — 這一行是多人共用頻道時唯一的防線。

✅ 骨架
USER.md 
# User

- **Workspace owner:** ___
- **Primary users:** ___、___、___
- **Language:** 繁體中文（台灣）
- **Timezone:** Asia/Taipei
- **Business context:** ___

## 角色關係

- ___（角色 A）可以查詢 ___，並可以 ___。
- ___（角色 B）可在授權範圍看到 ___，負責第一階段核准。
- ___（角色 C）擁有 ___ 的最終決定權。
- Workspace owner 管理系統設定，但不因此自動取得所有 ___。

無法確認呼叫者身分或權限時，只提供一般性說明，不回傳個人資料，也不執行寫入。
⚠️ 「Workspace owner 不等於全部權限」要明寫。否則設定這隻龍蝦的人會自動變成能看到所有敏感資料的人，這通常不是你想要的授權模型。

AGENTS.md — 作業規則（最重要的一份）

啟動順序、職責、作業原則、人工核准紅線、隱私邊界、回覆格式
必要規則
subagent 也會收到硬規則唯一的家含部署預設

如果只能寫一個檔案，就寫這個。它是政策層：Agent 怎麼開場、什麼可以自動做、什麼一定要人核准、輸出長什麼樣。子代理 session 只注入 AGENTS.md，所以任何你希望連子代理都遵守的規則，都必須在這裡，不能只寫在 SOUL.md。

✅ 建議七節骨架
AGENTS.md 
# ___-agent Workspace

## 啟動順序
優先使用 runtime 已載入的 workspace context；只有檔案未載入或需要刷新時，才依序讀取：
1. IDENTITY.md  2. SOUL.md  3. USER.md  4. TOOLS.md
5. MEMORY.md（只限 main session）
6. memory/YYYY-MM-DD.md（只限 main session；今天與昨天）
HEARTBEAT.md 只有在 heartbeat 事件發生時讀取。
群組、共享或跨 Agent 情境不得載入 MEMORY.md 或 daily memory。

## 部署預設
在 USER.md 尚未填妥正式角色、TOOLS.md 尚未配置可驗證的 API scope 前，
本 Agent 僅能唯讀查詢與產生草稿；所有正式寫入能力保持停用。

## 職責
（貼上 Part 1 的「職責範圍」3–5 條）
___ 是資料與規則的唯一權威。只透過 TOOLS.md 記載的 API 使用資料。

## 作業原則
1. 先確認 ___（範圍變數：日期／班別／單號／客戶）；資訊不足時列出缺口。
2. 查詢與分析可自動執行；寫入前先顯示預計動作、影響對象與依據。

## 回覆格式

Part 4 · 這隻龍蝦擁有哪些 Skills

工具已經有了，但需要「固定做法」的時候，才寫成 Skill
必填能力
SKILL.md + frontmatterskills/ 目錄描述決定觸發率

Skill 是裝進提示詞的指示套件：一個目錄加一份 SKILL.md（YAML frontmatter + Markdown 內文）。判準很簡單 — 工具（tool）是「能做什麼」，Skill 是「該怎麼做」。如果 Agent 已經有 exec、browser、API 工具，但每次做同一件事的步驟都不一樣、或常常漏掉某個檢查，那就該寫成 Skill。

  • description 是觸發器，不是簡介。Skill 會被壓縮成 XML 注入系統提示，模型只靠 description 判斷「現在該不該用」。所以要把使用者實際會說的話寫進去（「部署 stage」「推 stage」），而不是寫「本技能提供部署功能」。
  • 它需要哪些工具才成立？如果需要特定執行檔或環境變數，用 metadata.openclaw.requires 做 gating（bins / env / config），環境不滿足就不要出現在提示詞裡。

Part 5 · 這隻龍蝦擁有哪些 Cron Jobs

不需要人開口就會發生的事 — 也是最容易變成噪音的部分
必填排程
openclaw automationsmain / isolated / session:Gateway 必須在跑

Automations（別名 cron）是 OpenClaw 內建的排程器：跑在 Gateway 行程裡，不在模型裡 — Gateway 沒開，排程不會觸發。任務定義與執行歷史存在共用的 SQLite 狀態庫，重啟不會掉。

⏰ Cron 清單（從 Part 2 日常裡「不需要人開口」的列挑出來）
cron-plan.md 
| # | 名稱        | 排程          | session   | 它要做什麼        | 送到哪            | 沒事時會不會出聲 |
|---|-------------|---------------|-----------|-------------------|-------------------|------------------|
| 1 | ___         | 0 8 * * 1-5   | isolated  | ___               | Slack #___        | 不出聲           |
| 2 | ___         | 0 18 * * 5    | session:___ | ___             | ___               | 出聲（週報）     |
| 3 | ___         | */30 * * * *  | main      | ___（只送 event） | 主 session        | 不出聲           |

✅ 建立指令範本
bash 
# 每天早上的巡檢 → 獨立 session、跑完丟 Slack
openclaw automations create "0 8 * * 1-5" \
  "檢查今天的 ___，列出異常與缺口；沒有異常就回覆『無異常』並結束。" \
  --name "___ 早班巡檢" \
  --tz "Asia/Taipei" \
  --session isolated \
  --announce --channel slack --to "channel:___"

# 每週報告 → 用固定 session，讓它記得上週寫過什麼
openclaw automations create "0 18 * * 5" \
  "彙整本週 ___，並與上週摘要比較差異。" \
  --name "___ 週報" --tz "Asia/Taipei" --session "session:___-weekly"

# 只想把事情排進主 session、不另外開一輪對話
openclaw automations create "*/30 * * * *" \
  --name "___ 佇列檢查" \
  --session main --system-event "檢查 ___ 佇列" --wake next-heartbeat

# 一次性提醒，跑完自動刪除
openclaw automations create "20m" \
  --name "___ 回檢" --session main \
  --system-event "回頭確認 ___" --wake now --delete-after-run
🔧 常用參數（填表時會用到）
參數用途怎麼選
--cron / 直接給表達式週期排程5 或 6 欄位 cron 表達式
--every / --at固定間隔 / 一次性"10m"、"1h" / ISO 時間或 "20m"
--session跑在哪個 sessionmain（進主對話）／isolated（全新 session，最乾淨）／session:自訂 id（跨次累積上下文，適合週報）
--tz時區台灣一律 "Asia/Taipei"，別靠伺服器預設
--system-event vs 提示字串要不要跑一輪模型只想排隊提醒 → --system-event（僅 main session）；要它真的做事 → 直接給 prompt
--announce --channel --to結果送去哪Slack／Telegram／Discord／Matrix，或 --webhook
--wake now｜next-heartbeat要不要立刻喚醒緊急 → now；可以等 → next-heartbeat
--stagger / --exact抖動 / 精準時間多個排程同時到點時用 --stagger 30s 錯開
--delete-after-run跑完自刪一次性提醒必加，否則會留一堆死任務
--enabled / --disabled先建好但不啟用新龍蝦建議先 --disabled，觀察幾次手動 run 的結果再啟用
ℹ️ 管理指令：openclaw automations list --all（含停用）、show 任務id（看解析後的投遞設定）、run 任務id（立刻試跑）、runs --id 任務id（執行歷史）、disable / remove。連續失敗會自動指數退避（30s → 1m → 5m → 15m → 60m），成功後回到正常排程。
⚠️ 每個排程都要回答「沒事的時候會不會出聲」。一隻每天早上都在群組說「今日無異常」的龍蝦，兩週後就會被所有人忽略 — 連它真的有異常那天也一起被忽略。預設：沒異常就安靜。

Part 6 · 需要記住哪些東西（Memory 設計）

兩層記憶：精煉的 MEMORY.md 與逐日的 memory/YYYY-MM-DD.md
必填記憶
MEMORY.md ＝精煉層daily ＝工作層memory_search / memory_get

  • 記憶會不會過期？寫下會影響未來行為的決策時，一定要標明時效邊界：核准狀態、暫時性限制、失效條件、什麼時候該重新確認。沒有時效的「已核准」，三個月後會變成越權的藉口。
