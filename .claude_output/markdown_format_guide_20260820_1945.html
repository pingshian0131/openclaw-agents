Markdown 是什麼？

一種用純文字寫、能轉成 HTML 的輕量標記語言
核心觀念
.md.markdown.mdxtext/markdown

Markdown 由 John Gruber 與 Aaron Swartz 於 2004 年提出，設計目標只有一句話：「讓文件在未經轉換的原始狀態下就易於閱讀」。它用 #、*、- 這類本來就常見於純文字信件的符號來表達結構，因此即使不經任何渲染，raw 檔案也看得懂 — 這是它跟 HTML、LaTeX、Word 最大的差別。

一個 .md 檔案本質上就是純文字檔（plain text），沒有二進位格式、沒有壓縮、沒有專屬 schema。你可以用 cat、git diff、任何編輯器直接開，也因此它天然適合版本控制。

📄 一個最小的 .md 檔案長什麼樣
README.md 

# 專案名稱

這是一段**說明文字**，描述專案用途。

## 安裝

```bash
npm install my-package
```

## 特色

- 輕量、零依賴
- 支援 TypeScript
- [線上文件](https://example.com)
ℹ️ Markdown 不是排版工具 — 它只描述「語意結構」（這是標題、這是清單），實際外觀由渲染端的 CSS 決定。想精準控制字型大小、顏色、位置，就得回頭用 HTML/CSS。
✅ 為什麼工程界普遍採用
為什麼是 Markdown 

1. Diff 友善     → 純文字，git diff 逐行可讀，PR review 容易
2. 零鎖定       → 不依賴任何軟體，任何編輯器都能開
3. 寫作專注     → 不用滑鼠切格式，手不離鍵盤
4. 到處都能渲染  → GitHub / GitLab / Slack / Notion / Discord 原生支援
5. 可程式化     → 容易被腳本、靜態網站產生器、LLM 解析與生成
6. 長期保存     → 20 年後仍然是可讀的 txt，沒有格式失效問題

標題 Heading

用 # 數量表示層級，對應 HTML 的 h1 ~ h6
基礎語法
ATX 風格Setext 風格

標題有兩種寫法。ATX 風格（# 開頭）是現在的主流，支援 1~6 級；Setext 風格（底線 === / ---）只支援 2 級，現在較少用，但在某些舊文件仍會看到。

📝 語法
heading.md 

# 一級標題 (h1)
## 二級標題 (h2)
### 三級標題 (h3)
#### 四級標題 (h4)
##### 五級標題 (h5)
###### 六級標題 (h6)

Setext 風格一級標題
==================

Setext 風格二級標題
------------------
⚠️ 常見錯誤：# 與文字之間必須有空格。#標題 在 CommonMark / GFM 下不會被當成標題，只會輸出成純文字 #標題。
ℹ️ 層級不要跳號 — 從 # 直接跳到 ### 會破壞文件大綱（outline）與螢幕閱讀器的導航。慣例上一份 .md 只有一個 # 一級標題當文件主題，其餘用 ## 起算。

段落與換行

Markdown 最容易踩坑的地方：按 Enter 不一定會換行
基礎語法

Markdown 用空行分隔段落。在同一段落內單純按一次 Enter，渲染後不會換行，兩行會被接成同一行 — 這是初學者最常遇到的困惑。要在段落內強制換行有三種做法。

⚠️ 不會換行的寫法
wrong.md 

第一行文字
第二行文字

渲染結果 → 第一行文字 第二行文字   (被接成一行)
✅ 三種正確的換行方式
correct.md 

方式 1：行尾加兩個以上空格（最標準，但空格看不見易被編輯器吃掉）
第一行文字··
第二行文字

方式 2：行尾加反斜線（CommonMark 支援，語意明確）
第一行文字\
第二行文字

方式 3：直接寫 HTML 標籤（最保險，各家渲染器都吃）
第一行文字<br>
第二行文字

段落切換：中間空一行（最推薦，語意最清楚）

這是新的一個段落。
ℹ️ 部分平台（GitHub 的 issue / PR 留言、Slack、Discord）啟用了 breaks 選項，單一 Enter 就會換行。但 GitHub 上 .md 檔案本身的渲染不啟用，所以同一份文字在留言框跟檔案裡會有不同結果。

文字強調 Emphasis

粗體、斜體、刪除線、行內程式碼
基礎語法
bolditalicstrikethroughinline code

星號 * 與底線 _ 效果相同，但底線在單字中間不會生效（避免誤傷 snake_case_name 這種變數名稱），所以慣例上一律用星號。

📝 語法
emphasis.md 

*斜體*            或  _斜體_            → <em>
**粗體**          或  __粗體__          → <strong>
***粗斜體***      或  ___粗斜體___      → <strong><em>
~~刪除線~~                              → <del>   (GFM 擴充)
`行內程式碼`                             → <code>
==高亮==                                 → <mark>  (Obsidian / Pandoc)

行內程式碼含反引號時，用更多反引號包住：
``含有 ` 反引號的程式碼``
⚠️ 中文的斜體陷阱：*中文* 在部分嚴格遵守 CommonMark 的渲染器中會失效，因為規格判斷「左右定界符」時依賴 Unicode 標點/空白規則，中文字元容易讓 * 被判定為非開啟符號。保險做法是在星號與中文之間避免緊鄰標點，或改用 <em> 標籤。

清單 List

無序清單、有序清單、嵌套、任務清單
基礎語法含 GFM
ulolnestedtask list

無序清單用 -、* 或 +；有序清單用 數字.。嵌套靠縮排，慣例縮 2 或 4 個空格（同一份文件內務必統一，混用是 bug 溫床）。任務清單（task list）是 GitHub Flavored Markdown 的擴充，在 GitHub 上會渲染成可點擊的 checkbox。

📝 語法
list.md 

無序清單：
- 項目一
- 項目二
  - 嵌套項目（縮排 2 空格）
    - 再一層
- 項目三

有序清單：
1. 第一步
2. 第二步
   1. 子步驟
3. 第三步

數字可以全寫 1.，渲染時會自動編號（好處：中間插入不用重排）：
1. 第一步
1. 第二步
1. 第三步

任務清單（GFM 擴充）：
- [ ] 未完成的待辦
- [x] 已完成的待辦
- [ ] ~~取消的項目~~

清單項目內含多段落（後續段落縮排對齊文字）：
- 這是項目的第一段。

  這是同一個項目的第二段，縮排 2 空格。

  ```bash
  # 清單內也能放程式碼區塊
  echo "hello"
  ```
ℹ️ 鬆散 vs 緊湊清單：項目之間有空行 → 每個項目被包成 <p>（鬆散，行距較大）；沒有空行 → 直接是 <li> 文字（緊湊）。想調整清單視覺密度時，這就是唯一的控制點。

連結與圖片

inline / reference / autolink 三種形式
基礎語法
inline linkreference linkautolinkimage

圖片語法就是連結語法前面加一個 !，方括號內的文字變成 alt 屬性。Reference link（參照式）把 URL 集中放在文件底部，適合同一個網址被引用多次、或 URL 很長會影響原始碼可讀性的情況。

📝 語法
link.md 

Inline 連結：
[顯示文字](https://example.com)
[帶 title 的連結](https://example.com "滑鼠停留時的提示")
[相對路徑連結](./docs/setup.md)
[跳到本頁標題](#安裝)          <- anchor 由標題文字轉小寫、空格轉 -

Reference 連結（URL 定義在文件底部，不會被渲染出來）：
請參考 [官方文件][docs] 與 [API 說明][api]。

[docs]: https://example.com/docs
[api]: https://example.com/api "API Reference"

Autolink（GFM 會自動偵測，純 CommonMark 需用角括號）：
<https://example.com>
<someone@example.com>

圖片：
![替代文字](./assets/screenshot.png)
![帶 title 的圖](https://example.com/img.png "圖說")

可點擊的圖片（圖片包在連結裡）：
[![Build Status](https://ci.example.com/badge.svg)](https://ci.example.com)
⚠️ Markdown 原生無法控制圖片尺寸。需要縮放時只能寫 HTML：<img src="x.png" width="400">。（例外：Obsidian 支援 ![[img.png|400]]、部分渲染器支援 ![alt](x.png =400x)，但都非標準。）

程式碼區塊 Code Block

Fenced code block 與語法高亮
基礎語法
inline codefencedindentedsyntax highlight

程式碼區塊有兩種：fenced（三個反引號或三個波浪號包住，可標語言）與 indented（每行縮排 4 空格，舊語法）。實務上一律用 fenced，因為可以指定語言做語法高亮，也不會跟清單縮排打架。

📝 語法（用 ~~~ 示範以免反引號混淆）
code.md 

行內程式碼用單反引號：請執行 `npm install`。

Fenced code block（三個反引號 + 語言標籤）：
~~~python
def greet(name: str) -> str:
    return f"Hello, {name}!"
~~~

~~~bash
git commit -m "feat: add markdown parser"
~~~

~~~diff
- const old = 1;
+ const new = 2;
~~~

不指定語言（不做高亮，適合純文字輸出、目錄樹）：
~~~
project/
├── src/
└── README.md
~~~

Indented code block（縮排 4 空格，舊寫法，不推薦）：

    這是程式碼
    這也是
ℹ️ 要在 code block 裡放 code block？外層用更多的圍欄符號即可 — 內層 3 個反引號，外層就用 4 個反引號（或改用 ~~~）。這在寫「教 Markdown 的 Markdown」時很常用。
ℹ️ 語言標籤的額外用途：除了高亮，mermaid（流程圖）、math / latex（公式）等標籤在 GitHub、Obsidian 等平台會被特殊渲染成圖表，而不是純文字程式碼。

引用區塊 Blockquote

> 開頭，可嵌套，GitHub 額外支援 Alert 語法
基礎語法含 GFM

用 > 開頭表示引用。引用區塊內可以再放任何 Markdown 元素（標題、清單、程式碼），也可以嵌套。GitHub Alerts 是 GFM 較新的擴充，用 > [!NOTE] 這種標記讓引用變成帶顏色與圖示的提示框。

📝 語法
quote.md 

> 這是一段引用文字。
> 同一個引用的第二行。

> 引用內可以放其他元素：
>
> - 清單項目
> - 另一個項目
>
> **粗體** 也可以。

嵌套引用：
> 第一層引用
> > 第二層引用
> > > 第三層引用

GitHub Alerts（GitHub / GitLab 支援，其他平台退化成普通引用）：
> [!NOTE]
> 一般提示資訊。

> [!TIP]
> 實用小技巧。

> [!IMPORTANT]
> 使用者必須知道的重點。

> [!WARNING]
> 需要立即注意的風險。

> [!CAUTION]
> 可能造成負面後果的操作。

表格 Table

GFM 擴充語法，用 | 分隔欄位
GFM 擴充

表格不在原始 Markdown 與 CommonMark 規格內，是 GFM（GitHub Flavored Markdown）的擴充，但今天絕大多數渲染器都支援。第二行的分隔列用冒號位置控制對齊。

📝 語法
table.md 

| 欄位 A | 欄位 B | 欄位 C |
| ------ | ------ | ------ |
| 資料 1 | 資料 2 | 資料 3 |
| 資料 4 | 資料 5 | 資料 6 |

對齊控制（冒號位置決定）：
| 左對齊 | 置中 | 右對齊 |
| :----- | :--: | -----: |
| left   | mid  |  right |

原始碼的管線符號不需要對齊，以下同樣合法（醜但可用）：
| 欄位 A | 欄位 B |
|---|---|
| 1 | 2 |

儲存格內可用行內語法，但不能有換行：
| 項目 | 說明 |
| --- | --- |
| `code` | **粗體** 與 [連結](https://example.com) |
| 換行 | 只能用 <br> 標籤硬換 |
⚠️ 表格的三個硬限制：(1) 儲存格內不能放多行內容，換行只能用 <br>；(2) 不支援合併儲存格（colspan / rowspan），需要就得改寫 HTML <table>；(3) 儲存格內文字含 | 必須跳脫成 \|，否則會被當成欄位分隔。

分隔線、跳脫字元與行內 HTML

其餘常用的零碎語法
基礎語法
horizontal ruleescapeinline HTMLcomment

Markdown 規格明確允許直接內嵌 HTML — 這是它的逃生門：語法做不到的（圖片尺寸、合併儲存格、折疊區塊、置中），一律用 HTML 補。但要注意許多平台（GitHub、Notion）會出於安全過濾掉 <script>、<style> 與部分屬性。

📝 語法
misc.md 

分隔線（三個以上，三種寫法等價）：
---
***
___

跳脫字元（讓符號顯示成字面意思，不被當語法）：
\*不是斜體\*        → *不是斜體*
\# 不是標題
\`不是程式碼\`
可跳脫字元：\ ` * _ { } [ ] ( ) # + - . ! |

註解（HTML 註解，渲染時不顯示）：
<!-- 這段文字不會出現在渲染結果中 -->

行內 HTML（Markdown 做不到的事都靠這個）：
<div align="center">置中的內容</div>

<details>
<summary>點擊展開（GitHub 上的折疊區塊）</summary>

這裡是折疊起來的內容，前後要留空行才會渲染 Markdown。

</details>

<kbd>Cmd</kbd> + <kbd>C</kbd>   → 顯示成按鍵樣式
<sub>下標</sub> 與 <sup>上標</sup>
⚠️ HTML 區塊內的 Markdown 不會被解析（CommonMark 規則）。<div>**粗體**</div> 會輸出字面上的星號。解法是在 HTML 標籤與內容之間空一行，如上面 <details> 的範例。

Front Matter — 檔案的 metadata

檔首的 YAML 區塊，靜態網站與筆記軟體的核心機制
進階應用
YAMLTOMLJekyll / HugoObsidian

Front matter 是放在檔案最開頭、由 --- 包住的結構化 metadata 區塊。它不屬於 Markdown 標準，而是工具層的慣例，但已經是事實標準：靜態網站產生器靠它決定標題、日期、標籤、模板；Obsidian 靠它做 properties 與 dataview 查詢；Claude Code 的 skill 與 agent 定義檔也用它宣告 name / description。

📄 典型的 front matter
posts/2026-08-20-hello.md 

---
title: "我的第一篇文章"
date: 2026-08-20
author: Ping
tags: [markdown, 教學, 工具]
draft: false
description: 介紹 Markdown 的基本語法與應用場景
---

# 我的第一篇文章

從這裡開始才是正文內容。
⚠️ --- 必須是檔案的第一行，前面不能有空行或 BOM，否則會被解析成分隔線（<hr>）而不是 front matter。這是設定沒生效時最常見的原因。

Markdown 方言（Flavors）差異

為什麼同一份 .md 在不同平台長得不一樣
進階應用易踩雷
Markdown.plCommonMarkGFMPandocMDXObsidian

Gruber 最初的規格寫得相當模糊，導致各家實作行為不一致。2014 年 CommonMark 出現，提供嚴格且有測試套件的規格，成為現代解析器的共同基礎；GFM 則是 GitHub 在 CommonMark 之上加的擴充（表格、任務清單、刪除線、autolink、alerts）。其他方言各自往不同方向長。

🔀 各方言的特色語法
flavors.md 

[GFM — GitHub / GitLab]
~~刪除線~~ 、 - [x] 任務清單 、 | 表格 |
https://自動連結 、 > [!WARNING] alerts
@mention 、 #123 issue 連結 、 :emoji:

[Pandoc — 學術寫作 / 轉檔]
腳註[^1] 、 定義清單 、 $LaTeX 公式$
[^1]: 這是腳註內容
表格 caption 、 引用文獻 [@citation]

[Obsidian — 個人知識庫]
[[Wiki 連結]] 、 [[檔案|顯示文字]] 、 ![[嵌入筆記]]
==高亮文字== 、 %%行內註解%% 、 #標籤

[MDX — React 文件網站]
import Chart from './Chart'
<Chart data={data} />      <- 直接在 Markdown 裡用 React component

[Notion / Slack — 部分支援]
沒有表格語法、標題只到 3 級、貼上時自動轉換為區塊
ℹ️ 實務建議：寫給多平台看的文件（README、規格書）就只用 CommonMark + GFM 的交集 — 標題、清單、粗斜體、連結、程式碼、表格、引用。方言特有語法留給那個平台專用的檔案。

工具生態與應用場景

.md 檔案實際被用在哪裡
進階應用
文件部落格筆記簡報AI / LLM

Markdown 早已超出「寫 README」的範疇。因為它同時對人類可讀與機器可解析，近年更成為 LLM 與 AI agent 的主要文件介面 — CLAUDE.md、skill 定義、prompt 模板、agent 輸出格式幾乎全是 Markdown。

🛠️ 場景與代表工具
ecosystem.txt 

專案文件      README.md / CHANGELOG.md / CONTRIBUTING.md / ADR
文件網站      MkDocs、Docusaurus、VitePress、Starlight、GitBook
靜態部落格    Hugo、Jekyll、Astro、Next.js (MDX)、Eleventy
知識管理      Obsidian、Logseq、Zettlr、Bear、Joplin
即時通訊      Slack、Discord、Teams（子集語法）
簡報          Marp、Slidev、reveal.js、Deckset
轉檔          Pandoc（→ PDF / docx / epub / LaTeX / HTML）
排版          Typora、iA Writer、VS Code + Markdown Preview
AI / LLM      CLAUDE.md、AGENTS.md、system prompt、agent skill 定義
資料交換      LLM 輸出格式、RAG 文件切塊、API 文件描述欄位
⚙️ 主流解析器（寫程式處理 .md 時會用到）
parsers.txt 

JavaScript   marked、markdown-it、remark / unified、micromark
Python       markdown-it-py、Python-Markdown、mistune、marko
Go           goldmark（Hugo 使用）、blackfriday
Rust         pulldown-cmark、comrak
Ruby         CommonMarker、Redcarpet
PHP          league/commonmark

- 清單前後也留空行
- 縮排統一用 2 或 4 空格，全檔一致
