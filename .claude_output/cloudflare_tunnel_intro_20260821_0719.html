🌩️ Cloudflare Tunnel 技術介紹報告

不開任何對外 port、不需要固定 IP、不必自己申請憑證，就能把本機或內網服務安全地掛在自有網域上 —— 從原理、四種建立方式、進階 ingress 設定，到與 ngrok 的取捨與實戰接 Webhook。

Cloudflare Tunnel cloudflared Zero Trust QUIC / HTTP2 自有網域 HTTPS 免費方案可用
⚡

一句話理解：Cloudflare Tunnel 讓你的伺服器主動向外連到 Cloudflare 的邊緣網路並保持長連線，之後所有外部請求都經由 Cloudflare 送進這條隧道 —— 所以防火牆完全不用開 inbound port，來源 IP 也不會外洩。它取代了「開 80/443 + 動態 DNS + 自己續憑證」這一整套傳統做法。

名詞對照表

Cloudflare 的命名沿革較多，先把新舊名稱與角色對清楚
ℹ️

歷史沿革：這項服務早期叫 Argo Tunnel（付費），後來免費開放並改名 Cloudflare Tunnel。設定介面則從 dash.cloudflare.com 移到 Zero Trust Dashboard（one.dash.cloudflare.com）底下的 Networks → Tunnels。網路上的舊教學若提到 Argo 或舊選單路徑，概念相同、位置已變。

名詞 類型 說明
Cloudflare Tunnel 服務 整體功能名稱。在 Cloudflare 邊緣與你的主機之間建立加密的持久出向連線，把流量導進內部服務。
cloudflared 本機 daemon 你要安裝的那支程式（Go 撰寫的單一 binary）。負責建立隧道、依 ingress 規則把請求轉給本機服務。
Connector 概念 一個正在運行的 cloudflared 實例。同一條 Tunnel 可以有多個 connector（不同機器同時跑），Cloudflare 會自動做負載平衡與容錯。
Quick Tunnel 模式 零設定、免帳號、免網域。執行一行命令就得到隨機的 *.trycloudflare.com 網址。僅供臨時測試，無 SLA、網址每次都變。
Named Tunnel 模式 正式做法。隧道有名字與 UUID、可綁自有網域、可重啟後沿用同一設定、可服務化常駐。
Locally-managed
（本機管理）		 設定方式 設定寫在本機 config.yml，用 CLI 管理。適合 IaC、版控、大量自動化部署。
Remotely-managed
（遠端管理）		 設定方式 設定存在 Cloudflare Dashboard，本機只需帶一個 token 執行。改設定不用登入主機，官方目前推薦此法。
Ingress rules 設定 「哪個 hostname／路徑 → 對應哪個本機 service」的對照規則清單，由上而下比對，最後必須有 catch-all。
<UUID>.cfargotunnel.com DNS 每條 Tunnel 的專屬內部目標。你的自訂網域會 CNAME 指到這裡（Cloudflare 代理的橘雲記錄）。
credentials file 金鑰 ~/.cloudflared/<UUID>.json，代表「這台機器有權替這條 Tunnel 建立連線」。等同密碼，不可外流。
cert.pem 金鑰 cloudflared tunnel login 後產生的帳號憑證，用來執行「建立隧道、寫 DNS」等管理操作。只有管理時需要，執行隧道本身不需要。
Zero Trust Access 選用功能 在 Tunnel 前面加一層身分驗證（Google / OTP / SSO），讓內部服務對外只有通過驗證者可見。
WARP 選用功能 Cloudflare 的客戶端。搭配 Tunnel 的 private network 模式，可讓遠端裝置直接存取內網 IP 網段（類 VPN），無需逐一開 hostname。

建立步驟總覽

先選路線，再照順序做 —— 三條路線的前置條件與適用情境不同

先決定走哪一條路線

路線 前置需求 網址 適用情境
A · Quick Tunnel 只要安裝 cloudflared 隨機
*.trycloudflare.com		 臨時 demo、給同事看五分鐘、快速驗證某個 webhook 能不能打進來。不要用於任何長期用途。
B · Named Tunnel（CLI） Cloudflare 帳號 + 網域已託管在 Cloudflare（NS 已改指） 自訂
app.example.com		 開發者本機長期使用、想把設定進版控、要用腳本自動化部署。
C · Dashboard（遠端管理） 同 B 自訂 團隊共用、不想登入主機改設定、需要在多台機器貼同一段安裝命令。官方推薦。
⚠️

路線 B/C 的硬門檻：網域的 nameserver 必須指向 Cloudflare。只把 DNS 記錄「抄」到 Cloudflare 是不夠的 —— 網域要完成 Cloudflare 的 onboarding（狀態顯示 Active）。這是與 ngrok 最大的差別：ngrok 直接借它的網域給你，Cloudflare 要你自備網域。

路線 B（CLI，最完整）的執行順序

Step 1 · 理解原理　閱讀，5 分鐘
先弄懂「出向連線」與 ingress 規則的比對順序，後面設定不會亂猜。
Step 2 · 安裝 cloudflared　≈ 2 分鐘
brew install cloudflared 或下載 binary。產出：cloudflared --version 有回應。
Step 3 ·（可選）Quick Tunnel 冒煙測試　≈ 1 分鐘
cloudflared tunnel --url http://localhost:8000 先確認本機服務與網路都正常，再投入正式設定。
Step 4 · 登入 → 建立 Tunnel → 綁 DNS → 寫 config → 啟動　≈ 10 分鐘
login → tunnel create → tunnel route dns → config.yml → tunnel run。產出：https://app.example.com 可對外服務。
Step 6 · 服務化常駐　≈ 3 分鐘
cloudflared service install（或 systemd / launchd / Docker），讓機器重開後自動連上。
Step 7 · 進階設定　依需求
多服務 ingress、HTTPS origin、originRequest 超時、路徑分流、metrics。
Step 8 · 加上 Access 存取控制　依需求
內部工具（Grafana、NAS、後台）務必套 Access 政策；對外 webhook 端點反而要設 Bypass，否則第三方服務會被登入頁擋住。

核心原理：為什麼不用開 port

出向長連線 + Anycast 邊緣 + ingress 分流

傳統做法 vs Tunnel 做法

項目傳統對外服務Cloudflare Tunnel
防火牆必須開 inbound 80/443，NAT 需 port forwarding零 inbound 規則；只需允許 outbound 到 7844
IP 需求固定公網 IP，或搭配 DDNS不需要，浮動 IP、CGNAT、行動網路皆可
TLS 憑證自行申請與續期（Let's Encrypt / ACME）Cloudflare 邊緣自動處理，本機可跑純 HTTP
來源 IP 暴露公開，容易被直接掃描與 DDoS完全隱藏，攻擊者只看得到 Cloudflare
DDoS / WAF需另建方案邊緣內建（WAF 規則依方案）
多機容錯需自建 LB同一條 Tunnel 跑多個 connector 即自動分流

連線建立的四個階段

  1. cloudflared 啟動並向外撥號。它主動連往 Cloudflare 邊緣（預設 QUIC over UDP 7844，失敗時退回 HTTP/2 over TCP 7844），並用 credentials 檔證明自己屬於這條 Tunnel。通常會同時建立四條連線到不同的邊緣資料中心，任一條斷線不影響服務。

  2. DNS 把使用者導到 Cloudflare。app.example.com 是一筆代理中（橘雲）的 CNAME，指向 <UUID>.cfargotunnel.com。使用者查 DNS 得到的是 Cloudflare 的 Anycast IP，永遠不會拿到你的真實 IP。

  3. 邊緣處理請求。就近的 Cloudflare 節點終止 TLS、套用 WAF／快取／Access 政策，再把請求塞進「那條已經存在的隧道」。

  4. cloudflared 依 ingress 規則轉發。由上而下比對 hostname 與 path，命中就轉給對應的本機 service（如 http://localhost:8000），回應循原路送回。

ingress 規則的比對邏輯

規則由上往下依序比對，第一個命中就停止 —— 順序寫錯會導致後面的規則永遠不會生效。清單最後一筆必須是沒有 hostname 的 catch-all，否則 cloudflared 會拒絕啟動。

ingress:
  # ① 最具體的先寫：hostname + path
  - hostname: app.example.com
    path: ^/api/.*
    service: http://localhost:9000

  # ② 同 hostname 的其他流量
  - hostname: app.example.com
    service: http://localhost:8000

  # ③ 別的 hostname
  - hostname: nas.example.com
    service: https://192.168.1.10:5001
    originRequest:
      noTLSVerify: true        # 自簽憑證的內網服務

  # ④ catch-all —— 必須存在且放在最後
  - service: http_status:404
⚠️

若把 - hostname: app.example.com（無 path）寫在 path: ^/api/.* 之前，API 的規則就永遠不會被命中 —— 這是設定 ingress 最常見的錯誤。

service 可以填什麼

寫法用途
http://localhost:8000最常見：轉給本機 HTTP 服務。
https://192.168.1.10:5001轉給內網其他主機的 HTTPS 服務（自簽憑證需 noTLSVerify）。
unix:/var/run/app.sock轉給 Unix socket，避免服務佔用 TCP port。
tcp://localhost:22任意 TCP（SSH、RDP、資料庫），客戶端需搭配 cloudflared access tcp。
ssh://localhost:22 / rdp://...語意化的 TCP，可搭配瀏覽器式終端。
bastion把這台當跳板，由客戶端指定最終目標。
http_status:404直接回固定狀態碼，catch-all 專用。

安裝 cloudflared

單一 binary，無執行期依賴

各平台安裝方式

# macOS（Homebrew）
brew install cloudflared

# Debian / Ubuntu（官方 apt repo，可隨系統更新）
sudo mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg \
  | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null
echo "deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main" \
  | sudo tee /etc/apt/sources.list.d/cloudflared.list
sudo apt-get update && sudo apt-get install -y cloudflared

# RHEL / CentOS / Fedora
sudo dnf install -y https://pkg.cloudflare.com/cloudflared-latest.x86_64.rpm

# Windows
winget install --id Cloudflare.cloudflared

# 任意 Linux：直接抓 binary
curl -L -o cloudflared \
  https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64
chmod +x cloudflared && sudo mv cloudflared /usr/local/bin/

# 驗證
cloudflared --version

Docker 使用方式（不裝在主機上）

# 遠端管理模式最適合容器化：只需要一個 token
docker run -d --name cloudflared --restart unless-stopped \
  cloudflare/cloudflared:latest tunnel --no-autoupdate run \
  --token eyJhIjoixxxx...
# docker-compose.yml —— 與應用容器同網段，service 直接寫容器名
services:
  app:
    image: my-app:latest
    expose: ["8000"]          # 不必 ports:，完全不對外

  cloudflared:
    image: cloudflare/cloudflared:latest
    restart: unless-stopped
    command: tunnel --no-autoupdate run
    environment:
      TUNNEL_TOKEN: ${CF_TUNNEL_TOKEN}
    depends_on: [app]
💡

容器化的最大好處：應用容器連 ports: 都不用宣告，主機上不存在任何對外監聽的 port，ingress 的 service 直接寫 http://app:8000（走 Docker 內部網路）。

路線 A：Quick Tunnel（零設定快速試）

一行命令、免帳號、免網域 —— 但只適合臨時用

操作

# 本機服務跑在 8000
cloudflared tunnel --url http://localhost:8000

終端機會印出類似訊息，其中的網址即可立刻對外使用：

+--------------------------------------------------------------------+
|  Your quick Tunnel has been created! Visit it at:                  |
|  https://random-words-here-1234.trycloudflare.com                  |
+--------------------------------------------------------------------+

Quick Tunnel 的限制（務必知道）

  • 網址每次重啟都不同，且完全隨機、無法指定。
  • 沒有可用性保證，Cloudflare 明確標示僅供測試，可能隨時中斷或被限流。
  • 無法套用 Access 政策、WAF 規則或任何 Zero Trust 設定（它不屬於你的帳號）。
  • 無法服務化常駐，關掉終端機就結束。
  • 網址是公開的，任何知道的人都能存取 —— 敏感服務不要這樣開。
適合：5 分鐘 demo 適合：驗證 webhook 通不通 不適合：任何長期用途

路線 B：Named Tunnel（CLI 本機管理）

完整五步：登入 → 建立 → 綁 DNS → 寫設定 → 啟動

4-1　登入並授權網域

cloudflared tunnel login

會自動開啟瀏覽器要你登入 Cloudflare 並選擇一個網域授權。完成後本機會產生 ~/.cloudflared/cert.pem。這個檔案只用於「管理」（建立隧道、寫 DNS 記錄），實際跑隧道時不需要它。

4-2　建立 Tunnel

cloudflared tunnel create my-app

# 輸出範例
# Tunnel credentials written to /Users/you/.cloudflared/6f2a...c3d1.json
# Created tunnel my-app with id 6f2a1b2c-3d4e-5f60-7a8b-9c0d1e2f3a4b

# 確認
cloudflared tunnel list
🔐

那個 <UUID>.json 是隧道憑證，任何拿到它的人都能冒充你的 connector 接管流量。權限設成 600，不要進 git，不要放進 Docker image。

4-3　把網域綁到這條 Tunnel

cloudflared tunnel route dns my-app app.example.com

# 效果等同於在 Cloudflare DNS 手動新增：
#   Type: CNAME
#   Name: app
#   Target: 6f2a1b2c-3d4e-5f60-7a8b-9c0d1e2f3a4b.cfargotunnel.com
#   Proxy status: Proxied（橘雲，必須開啟）
☁️

橘雲（Proxied）一定要開。若把該筆 CNAME 設成 DNS only（灰雲），流量不會經過 Cloudflare 邊緣，隧道就沒有入口，瀏覽器會拿到錯誤。

4-4　撰寫 config.yml

~/.cloudflared/config.yml 
tunnel: 6f2a1b2c-3d4e-5f60-7a8b-9c0d1e2f3a4b       # 或直接寫 tunnel 名稱
credentials-file: /Users/you/.cloudflared/6f2a1b2c-...json

# 連線行為（可選）
protocol: quic            # quic（預設）| http2；被 UDP 阻擋時改 http2
loglevel: info            # debug 時改 debug
metrics: localhost:2000   # /metrics 供 Prometheus 抓取
no-autoupdate: true       # 生產環境建議關閉自動更新，改由套件管理

ingress:
  - hostname: app.example.com
    service: http://localhost:8000
  - service: http_status:404
# 啟動前先驗證設定語法
cloudflared tunnel ingress validate

# 測試某個 URL 會命中哪一條規則（超好用）
cloudflared tunnel ingress rule https://app.example.com/api/users

4-5　啟動並驗證

cloudflared tunnel run my-app

成功時 log 會出現 Registered tunnel connection（通常四筆，對應四個邊緣資料中心）。此時開瀏覽器連 https://app.example.com 應直接看到你的本機服務。

# 另一個終端機驗證
curl -I https://app.example.com

# 看 Cloudflare 是否真的有處理（會有 cf-ray、server: cloudflare）
curl -sD - -o /dev/null https://app.example.com | grep -i 'cf-ray\|server'

路線 C：Dashboard 建立（遠端管理）

設定存在雲端，本機只執行一段帶 token 的命令

操作步驟

  1. 開啟 Zero Trust Dashboard：https://one.dash.cloudflare.com/

  2. 左側 Networks → Tunnels → Create a tunnel → 選 Cloudflared。

  3. 命名 Tunnel（例如 my-app）→ Save tunnel。

  4. 頁面會依作業系統列出安裝命令（內含 token），複製到目標主機執行即可 —— 它會同時完成安裝與服務註冊。

  5. 回到 Dashboard，等 connector 狀態變成 HEALTHY。

  6. 切到 Public Hostname 分頁 → Add a public hostname：填 Subdomain、選 Domain、Service 填 HTTP + localhost:8000 → Save。DNS 記錄會自動建立。

# Dashboard 給的命令長這樣（Linux 範例）
sudo cloudflared service install eyJhIjoiYWJjMTIz...很長的token...

兩種管理方式怎麼選

比較項本機管理（config.yml）遠端管理（Dashboard）
設定存放主機上的 YAMLCloudflare 雲端
改設定SSH 進主機改檔 + 重啟網頁點一點，即時生效不必重啟
版本控制可（YAML 進 git）不易（可用 Terraform / API 補足）
大量部署需自行配送 config 與 credentials同一段 token 命令貼到多台
離線可讀性設定一目瞭然必須上 Dashboard 才知道現在怎麼設
建議情境IaC 流程、單機開發、需要進版控團隊協作、多台 connector、非工程人員也要維護
⚠️

兩種方式不要混用。一條 Tunnel 若已在 Dashboard 設定 public hostname，本機的 config.yml 中的 ingress 會被忽略（遠端設定優先）。debug 時常見的「我明明改了 config 卻沒生效」就是這個原因。

服務化常駐

開機自動啟動、斷線自動重連

用內建命令安裝為系統服務

# 本機管理模式：會讀取 ~/.cloudflared/config.yml
sudo cloudflared service install

# 遠端管理模式：帶上 Dashboard 給的 token
sudo cloudflared service install <TOKEN>

# Linux（systemd）
sudo systemctl enable --now cloudflared
sudo systemctl status cloudflared
sudo journalctl -u cloudflared -f          # 看即時 log

# macOS（launchd）
sudo launchctl list | grep cloudflared

# 移除
sudo cloudflared service uninstall
📁

以 sudo 安裝服務時，設定檔會從 /etc/cloudflared/config.yml 讀取（而非你家目錄的那份）。安裝前記得把 config 與 credentials 複製到 /etc/cloudflared/，否則服務會抱怨找不到憑證。

自訂 systemd unit（需要更多控制時）

/etc/systemd/system/cloudflared.service 
[Unit]
Description=Cloudflare Tunnel
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
User=cloudflared
ExecStart=/usr/local/bin/cloudflared --no-autoupdate \
          --config /etc/cloudflared/config.yml tunnel run
Restart=always
RestartSec=5
# 安全強化：不需要 root，也不需要寫入檔案系統
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadOnlyPaths=/etc/cloudflared

[Install]
WantedBy=multi-user.target

cloudflared 不需要 root 權限即可運作（它不綁定低號 port），建立專用使用者執行是良好實務。

進階設定

多服務、超時、Header 改寫、監控、私有網段

7-1　一條 Tunnel 服務多個站台

tunnel: my-app
credentials-file: /etc/cloudflared/6f2a....json

ingress:
  # 前台
  - hostname: www.example.com
    service: http://localhost:3000

  # API（同網域不同路徑，注意要寫在 www 之前若同 hostname）
  - hostname: api.example.com
    service: http://localhost:8000
    originRequest:
      connectTimeout: 30s
      noHappyEyeballs: true

  # 內網 NAS（自簽憑證）
  - hostname: nas.example.com
    service: https://192.168.1.10:5001
    originRequest:
      noTLSVerify: true
      httpHostHeader: nas.local     # 後端用 Host 判斷虛擬主機時需要

  # SSH（客戶端用 cloudflared access ssh 連）
  - hostname: ssh.example.com
    service: ssh://localhost:22

  # WebSocket 服務不需特別設定，預設即支援
  - hostname: ws.example.com
    service: http://localhost:7000

  - service: http_status:404

7-2　originRequest 常用參數

參數預設用途
connectTimeout30s連到本機服務的建立連線超時。
noTLSVerifyfalse跳過 origin 憑證驗證。內網自簽憑證必用。
originServerName—指定 TLS SNI，讓自簽憑證能通過驗證。
httpHostHeader—改寫送往後端的 Host header，解決虛擬主機判斷錯誤。
disableChunkedEncodingfalse某些老舊 WSGI／IIS 後端不支援 chunked 時開啟。
keepAliveConnections100對 origin 的連線池大小，高併發可調高。
proxyType: socks—把這個 ingress 當 SOCKS5 代理出口。
access—在 cloudflared 層要求必須帶有效的 Access JWT，防止有人繞過邊緣直連。

# 開啟 metrics endpoint（config.yml: metrics: localhost:2000）
curl -s http://localhost:2000/metrics | grep cloudflared_tunnel

# 關鍵指標
#   cloudflared_tunnel_ha_connections          目前健康連線數（正常應為 4）
#   cloudflared_tunnel_total_requests          累計請求數
#   cloudflared_tunnel_request_errors          轉發到 origin 的錯誤數
#   cloudflared_tunnel_concurrent_requests_per_tunnel  併發量

# 遠端管理的 Tunnel 可從雲端拉即時 log（不必登入主機）
cloudflared tail --token <TOKEN>

# 本機除錯：把 log 級別開到 debug

🔍

沒有 ngrok 那種請求檢視器是 cloudflared 最明顯的體驗落差。替代方案：cloudflared tail 看即時請求摘要、Dashboard 的 Analytics 看流量統計，或在自己的應用裡加 request log middleware。要逐筆看 body，還是得自己記。

7-4　私有網段模式（類 VPN）

除了逐一對應 hostname，Tunnel 也能把整個內網 CIDR暴露給安裝了 WARP 的裝置。這時不需要為每個服務建 DNS 記錄，遠端裝置可直接用內網 IP 連線。

# 把 192.168.1.0/24 這個網段掛進 Tunnel
cloudflared tunnel route ip add 192.168.1.0/24 my-app

# 查看已註冊的路由
cloudflared tunnel route ip list

之後在 Zero Trust → Settings → WARP Client 設定 Split Tunnel 讓該網段走 Cloudflare，客戶端裝 WARP 並登入組織即可存取。適合取代傳統 VPN 存取內部資料庫、印表機、管理介面。

Zero Trust 存取控制

Tunnel 只解決「連得到」，Access 才解決「誰可以連」
🚨

Tunnel 本身不做身分驗證。只要把服務掛上 public hostname，全世界都能存取（跟你直接開 port 一樣，差別只在來源 IP 被隱藏）。內部工具、後台、監控面板務必再套一層 Access 政策。

8-1　為 hostname 加上登入驗證

  1. Zero Trust Dashboard → Access → Applications → Add an application → Self-hosted。

  2. Application domain 填 nas.example.com（與 Tunnel 的 public hostname 一致）。

  3. 新增 Policy：Action Allow，Include 條件可選 Emails（列舉允許的信箱）、Email domain（整個公司網域）、Identity provider group 等。

  4. 設定 identity provider：免費可用 One-time PIN（寄驗證碼到信箱），或接 Google / GitHub / Microsoft Entra ID / SAML。

  5. 存檔後再開該網址，會先跳 Cloudflare 的登入頁，通過才進得去。

8-2　機器對機器：Service Token

API 或 CI 無法做互動式登入。改發 Service Token，讓呼叫方帶兩個 header 通過驗證：

# Zero Trust → Access → Service Auth → Create Service Token
# 政策的 Include 條件選 "Service Auth" 並指定該 token

curl https://api.example.com/health \
  -H "CF-Access-Client-Id: 0a1b2c....access" \
  -H "CF-Access-Client-Secret: 9f8e7d...."

8-3　Webhook 端點的正確做法：Bypass

第三方服務（LINE、GitHub、Stripe）不可能通過 Cloudflare 的登入頁。若整個網域套了 Access，webhook 會全部收到 302 導向登入頁而失敗。

情境建議設定
整站是內部工具 整個 hostname 套 Allow 政策（Email / SSO）。
站內只有 /webhook 要對外 建立更具體的 Application（path 為 /webhook），政策 Action 設 Bypass + Everyone；其餘路徑維持 Allow。Access 以最具體的路徑優先。
webhook 專用子網域 把 hook.example.com 完全不套 Access，改用應用層簽章驗證（如 LINE 的 X-Line-Signature）。這是最乾淨的做法。
想再加一層防護 用 WAF Custom Rules 限制來源（LINE 有公布 webhook 來源 IP 區段可參考）、或限制 User-Agent、rate limit。
✅

原則：人用的介面靠 Access；機器打的端點靠應用層簽章。不要期待 Access 幫你擋 webhook 偽造，也不要用 Access 把合法 webhook 一起擋掉。

⚖️

  • 家用 NAS / 樹莓派 / homelab 對外 → Cloudflare Tunnel，免費、免固定 IP、隱藏家用 IP。
  • 純內部裝置互連、不需要對公網開放 → Tailscale 的 mesh 模式更直覺。
  • 兩者並用是常態：開發當下用 ngrok 看封包，穩定後改掛 Cloudflare Tunnel 常駐。

實戰：用 Cloudflare Tunnel 接 Webhook

以 LINE Messaging API 為例，取代 ngrok 的完整設定

目標架構

LINE Platform
    │  POST https://line-hook.example.com/webhook
    ▼
Cloudflare Edge  ──（WAF / Rate limit，Access 設 Bypass）
    │
    ▼  既有的出向隧道
cloudflared（你的機器 / VPS / 家用主機）
    │  http://localhost:8000/webhook
    ▼
FastAPI / Express（驗 X-Line-Signature → 回 200 → 呼叫 Reply API）

設定步驟

  1. 建立 Tunnel 並綁 webhook 專用子網域（與人用介面分開，權限設定不互相干擾）。

  2. ingress 指向本機服務。

  3. 確認該 hostname 沒有套 Access 政策，或明確設為 Bypass。

  4. 把 Webhook URL 填進 LINE Developers Console 並按 Verify。

  5. （選用）加 WAF 規則限制只允許 LINE 的來源網段與 POST 方法。

# 1~2：建立與綁定
cloudflared tunnel create line-bot
cloudflared tunnel route dns line-bot line-hook.example.com
~/.cloudflared/config.yml 
tunnel: line-bot
credentials-file: /Users/you/.cloudflared/<UUID>.json

ingress:
  - hostname: line-hook.example.com
    path: ^/webhook$                     # 只開放這一條路徑，其餘一律 404
    service: http://localhost:8000
  - hostname: line-hook.example.com
    service: http_status:404
  - service: http_status:404
# 4：確認外部連得到（LINE 的 Verify 會送 events:[] 的空 POST）
curl -i -X POST https://line-hook.example.com/webhook \
  -H "Content-Type: application/json" \
  --data-raw '{"destination":"U0","events":[]}'

# 預期 400（因為沒帶合法簽章）—— 代表流量已到你的程式，隧道正常

相較 ngrok 的實務差異

項目ngrokCloudflare Tunnel
Webhook URL 是否會變免費版重啟就變（除非用靜態網域）永不改變，Console 設一次就好
機器睡眠後需手動重啟並更新 URL服務化後自動重連，URL 不變
看單筆 request 內容:4040 完整 body + Replay需自己在應用內記 log
擋掉非法流量需自己在程式裡做可用 WAF / Rate Limiting 在邊緣擋掉
多人共用同一 ChannelURL 互相蓋掉各人用不同子網域，互不干擾
🔐

簽章驗證依然必做。Cloudflare 隱藏了你的 IP，但 hostname 是公開的 —— 任何人都能對 /webhook 發 POST。是否用 Tunnel 與是否要驗簽是兩件獨立的事。

限制與注意事項

上線前一定要知道的邊緣行為
項目行為影響與對策
上傳大小上限 Free 方案約 100 MB／請求 超過會回 413。大檔上傳請走直傳物件儲存（R2 / S3 presigned URL），不要穿隧道。
origin 回應超時 約 100 秒 超時回 524。長工作改為非同步任務 + 輪詢／WebSocket，不要讓單一請求跑幾分鐘。
可代理的 port 邊緣僅代理特定 HTTP(S) port 對外一律用 443（Tunnel 情境下你不需要在意本機 port，那是隧道內部的事）。
需要 UDP 7844 出向 QUIC 預設走 UDP 企業防火牆常封 UDP。改 protocol: http2（TCP 7844）即可，效能略降但相容性最好。
非 HTTP 協定 TCP/SSH/RDP 需客戶端配合 對方必須裝 cloudflared（cloudflared access tcp）或用 WARP，無法像 HTTP 那樣「開瀏覽器就能用」。
網域必須在 Cloudflare NS 需改指 公司網域由他人管理時會卡住。折衷做法：另買一個便宜網域專供開發用。
用戶端真實 IP 經過代理後 remote_addr 是 Cloudflare 應用要讀 CF-Connecting-IP（或 X-Forwarded-For 最左側）才拿得到真實來源 IP。
Quick Tunnel 無保證 隨時可能中斷／限流 永遠不要用於 demo 以外的場合。
設定衝突 遠端設定覆蓋本機 ingress 一條 Tunnel 只選一種管理方式，別混用。
自動更新 cloudflared 預設會自我更新並重啟 生產環境設 no-autoupdate: true，改由套件管理器控制版本，避免半夜自己重啟。

疑難排解對照表

依症狀查，先分辨問題在「邊緣到隧道」還是「隧道到本機」
🧭

分層判斷法：① curl -I https://app.example.com 看回應是否帶 server: cloudflare（有 → DNS 與邊緣沒問題）；② 看 cloudflared log 有沒有 Registered tunnel connection（有 → 隧道通）；③ 在主機上 curl http://localhost:8000（通 → 本機服務正常）。三段各自確認，就能一次定位。

症狀原因解法
error 1033
Argo Tunnel error		 DNS 指向某條 Tunnel，但該 Tunnel 目前沒有任何 connector 在線。 啟動 cloudflared；確認 cloudflared tunnel list 中該 Tunnel 有 connections；確認 CNAME 指到正確的 UUID。
error 502 / 1016 隧道通了但轉不到本機服務：port 錯、服務沒起、service 寫成 https 但後端是 http。 主機上先 curl 一次確認；核對 ingress 的 scheme 與 port。
error 526
Invalid SSL certificate		 ingress 寫 https:// 但後端是自簽憑證。 加 originRequest.noTLSVerify: true，或改用 http://（隧道內已加密）。
error 524 後端超過約 100 秒才回應。 改非同步處理；別在請求內做長工作。
413 Payload Too Large 上傳超過方案上限。 改走物件儲存直傳；或升級方案。
網址一直是 Cloudflare 的預設頁 / DNS 錯誤 CNAME 未建立、或設成 DNS only（灰雲）。 DNS 頁確認該筆為 CNAME → <UUID>.cfargotunnel.com 且 Proxied。
改了 config.yml 但沒有生效 ①這條 Tunnel 是遠端管理，ingress 被 Dashboard 覆蓋；②服務讀的是 /etc/cloudflared/config.yml 不是家目錄那份；③沒重啟服務。 確認管理方式；用 --config 明確指定路徑；systemctl restart cloudflared。
啟動時報 ingress 驗證失敗 缺少 catch-all，或 YAML 縮排錯誤。 最後補 - service: http_status:404；跑 cloudflared tunnel ingress validate。
連線頻繁斷開／延遲高 網路封鎖 UDP 7844，QUIC 一直重試。 設 protocol: http2 改走 TCP；或請網管放行 UDP 7844 出向。
failed to create tunnel: Cannot determine default origin certificate path 沒有 cert.pem（未執行 login）。 跑 cloudflared tunnel login；或用 --origincert 指定路徑。
webhook 全部收到 302 導到登入頁 該 hostname 套了 Access 政策。 為 webhook 路徑建 Bypass 政策，或改用未套 Access 的專用子網域。
應用取到的 client IP 都是 Cloudflare 經過反向代理的正常現象。 改讀 CF-Connecting-IP header。
服務半夜自己重啟 cloudflared 自動更新。 設 no-autoupdate: true 或加 --no-autoupdate。
刪不掉 Tunnel 還有 connector 在線或有 DNS 記錄指著。 cloudflared tunnel cleanup <NAME> 清掉連線後再 tunnel delete；順手刪 DNS 記錄。
