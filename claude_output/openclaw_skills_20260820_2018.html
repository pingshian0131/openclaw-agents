Skill 是什麼 — 教 Agent「什麼時候該用哪個工具」

不是程式碼，是一份會被載入 system prompt 的 Markdown 指示檔
基礎概念
Markdown 指示檔SKILL.md漸進式揭露

OpenClaw 的 Skill 是Markdown 指示檔，用來教 Agent 什麼時候、以及如何使用工具。每個 Skill 是一個目錄，裡面必須有一份 SKILL.md（含 YAML frontmatter 與 Markdown 內容）。

關鍵理解在於它和 plugin / MCP 的分工：plugin 與 MCP 提供「能力」（真正可呼叫的工具），Skill 提供「判斷與流程」——什麼情況該啟動、要按什麼順序做、輸出要長什麼樣、哪些邊界不能踩。所以一個 Skill 常常一行程式碼都沒有，卻能大幅改變 Agent 的行為品質。

📐 運作模型：只有描述進 prompt，內文用到才讀

Skill 採用漸進式揭露（progressive disclosure）：平常只有 name 與 description 被編進 system prompt（每個 Skill 大約 97 個字元 + 欄位長度，約 24 tokens），Agent 判斷相關時才去讀完整的 SKILL.md 與附帶檔案。這是它能「裝很多但不吃 context」的原因。

ℹ️ 推論結果：description 是整個 Skill 最重要的一行。它是唯一常駐 prompt 的內容，也是模型判斷「要不要載入我」的唯一依據。內文寫得再好，description 沒寫對就不會被觸發。

SKILL.md 結構與 frontmatter 欄位

兩個必填欄位就能跑，其餘欄位決定它怎麼被觸發
必讀格式
namedescriptionuser-invocablecommand-dispatch
✅ 最小可用 Skill
~/.openclaw/workspace/skills/my-skill/SKILL.md 

---
name: my-skill
description: What this skill does
---

Instructions for when and how to use tools...
🏷️ 必填欄位的規則

name：小寫 slug，只允許英文字母、數字與連字號（ClawHub 規範為 1–64 字元）。description：單行、建議 160 字元以內——這是 Agent 看得到的說明，也用於 UI 摘要與搜尋。

⚙️ 控制觸發行為的選用欄位
frontmatter 

---
name: deploy-stage
description: 部署到 stage 環境並監控 CI pipeline
version: 1.2.0
user-invocable: true            # 是否顯示為 slash command（預設 true）
disable-model-invocation: false # true = 不編進 prompt，模型不會自己叫它
command-dispatch: tool          # 直接路由到工具，跳過模型層
metadata:
  openclaw:
    requires:
      bins: ["glab"]
      env: ["GITLAB_TOKEN"]
---
ℹ️ user-invocable 與 disable-model-invocation 是兩個獨立開關，組合起來有四種行為：兩者皆預設 = 模型可自己觸發 + 也能打 slash command；disable-model-invocation: true = 純手動指令（不佔 prompt token）；user-invocable: false = 只有模型能用，使用者打不出來。

六層載入優先序

同名 Skill 時，優先序高的來源勝出（不合併）
重要路徑
由高到低 

1. Workspace skills        <workspace>/skills
2. Project agent skills    <workspace>/.agents/skills
3. Personal agent skills   ~/.agents/skills
4. Managed skills          ~/.openclaw/skills      ← openclaw skills install 的預設落點
5. Built-in skills         隨安裝內建
6. Extra directories       skills.load.extraDirs + plugin 提供的 skills

當同一個 Skill 名稱出現在多個位置時，優先序最高的來源勝出。這給了一個實用手法：想改內建或已安裝的 Skill，不要去改原檔，在 workspace 建一個同名 Skill 覆蓋它——升級不會被蓋掉，也隨時可以刪掉還原。

ℹ️ 層級的用意：1–2 是「這個專案／這個 Agent 專屬」，3 是「我個人到處都想用」，4 是「從 ClawHub 裝來的」，5–6 是系統與外掛提供的底層。愈靠近工作現場，優先序愈高。
4

三種觸發路徑 — 模型自主、slash command、直達工具

command-dispatch: tool 是「確定性執行」的關鍵
核心行為
① 模型自主觸發

Skill 的 name/description 被編進 system prompt，模型自行判斷相關時載入並依指示執行。適合「使用者不會記得有這個功能」的情境。

② Slash command（user-invocable）

可被使用者呼叫的 Skill 會自動暴露成 slash command。兩種入口：註冊成直接指令（例如 /prose），或走通用入口 /skill <name> [input]。原生指令註冊由 commands.nativeSkills 控制（Discord / Telegram 上會自動註冊原生指令）。

③ command-dispatch: tool — 跳過模型層

宣告 command-dispatch: tool 的 Skill 會直接、確定性地路由到工具，繞過模型層。這是「這個指令必須每次都做同一件事」的正確做法——不讓模型有詮釋空間，也省下一輪推論。

⚠️ 別把需要判斷的流程設成 command-dispatch: tool。它的價值正是「沒有判斷」；需要看情況調整步驟的 Skill 應該留給模型執行。
5

條件式 gating — 依賴不齊就不載入

metadata.openclaw.requires：bins / env / config 三種條件
實用環境
SKILL.md frontmatter 

metadata:
  openclaw:
    requires:
      bins:    ["required-tool"]   # 必須存在於 PATH
      anyBins: ["docker", "podman"] # 至少一個存在即可
      env:     ["API_KEY"]          # 環境變數必須存在
      config:  ["feature.enabled"]  # 設定路徑必須為 truthy
    envVars:      # 詳細宣告，可標記 required
      - name: API_KEY
        required: true
    primaryEnv: API_KEY   # 主要認證變數

Skill 只有在所有列出的執行檔存在於 PATH、環境變數齊備、且設定路徑為 truthy 時才會載入。

ℹ️ gating 的真正好處是省 prompt。沒裝 glab 的機器上，GitLab 相關 Skill 完全不會出現在 system prompt 裡——既不浪費 token，也不會讓模型建議一個根本跑不起來的流程。
6

{baseDir} 與附帶檔案

Skill 目錄可以放範本、參考文件與腳本，用 token 引用不寫死路徑
技巧結構

Skill 目錄除了 SKILL.md（也接受舊名 skills.md）之外，可以放任意支援檔案：HTML 範本、參考資料、腳本，並可用 .clawhubignore / .gitignore 排除不想發布的檔案。

引用這些檔案時用 {baseDir} token，它會指向 Skill 自己的目錄，不需要寫死絕對路徑——這讓同一份 Skill 在不同機器、不同安裝位置都能正常運作。

SKILL.md 內文 

產生報告前先讀取範本作為結構基礎：

| 模板 | 路徑 |
|------|------|
| 分析報告 | {baseDir}/assets/template-analysis-report.html |
| QA 報告  | {baseDir}/assets/template-qa-report.html |
ℹ️ 這正是漸進式揭露的第三層：description 在 prompt（永遠載入）→ SKILL.md 內文（相關時載入）→ 附帶檔案（真正要用時才讀）。大範本、長參考資料都該放在第三層。
7

Token 成本、快照與刷新時機

Skill 在 session 開場被快照；改了檔案不一定立刻生效
重要執行期
約 24 tokens / skillsession 開場快照skill watcher

成本：每個符合條件的 Skill 為 system prompt 增加約 97 個字元加上欄位長度，換算大約 24 tokens（未計欄位長度）。所以裝 50 個 Skill 大約是一千多 tokens 的固定開銷——不算貴，但這也解釋了為什麼 description 要精簡、以及為什麼要用 gating 把不相關的 Skill 擋掉。

快照：Skill 在 session 開始時被快照，並在該 session 後續所有輪次重複使用。單純改檔案，變更會在下一個新 session 生效。

✅ session 進行中會刷新的兩種情況
刷新條件 

1. skill watcher 偵測到 SKILL.md 變更   （需 skills.load.watch 啟用）
2. 有新的符合條件的遠端節點連線
⚠️ 開發 Skill 時最常見的困惑就在這裡：改完 SKILL.md 卻發現行為沒變。先確認 skills.load.watch 是否啟用，否則就開一個新 session 再測。

可見性與 allow list — 哪個 Agent 看得到哪些 Skill

非空清單「完全取代」預設值，不是合併
易踩雷設定

Skill 的可見性和它放在哪裡是兩件獨立的事。放進 workspace 不代表每個 Agent 都會看到——實際可見範圍由 allow list 決定。

openclaw.json 

agents: {
  defaults: { skills: ["github", "weather"] },
  list: [
    { id: "writer" },              // 繼承 defaults
    { id: "locked-down", skills: [] }  // 完全沒有 skill
  ]
}
⚠️ 非空的 agent skill 清單會「完全取代」defaults，不會合併。想在某個 Agent 上「加一個」Skill，必須把 defaults 的內容整份重列一次，否則其他 Skill 會靜默消失。
⚠️ allow list 是可見性過濾器，不是 shell 執行的授權邊界。官方明確標註了這點——想限制執行權限要用 sandbox 與工具政策，不能靠隱藏 Skill 達成安全。
9

環境變數注入 — 以及 sandbox 陷阱

注入只作用於 host 執行，sandbox 內要另外設定
安全執行期
🔄 執行時的四個步驟
Skill 執行流程 

1. 解析該 Agent 的有效 skill 清單
2. 把 skills.entries.<key>.env 與 apiKey 注入行程環境
3. 把符合條件的 skills 編進 system prompt
4. 執行結束後還原原本的環境
⚠️ 環境變數注入僅限於 host agent 執行，不含 sandbox。若 Skill 跑在沙箱裡，憑證要另外設定在 agents.defaults.sandbox.docker.env 之下。這是「本機測得通、上了沙箱就 401」最常見的原因。
10

openclaw.json 的 skills 設定

load / install / workshop 三組設定
參考設定
~/.openclaw/openclaw.json 

skills: {
  load: {
    extraDirs: ["/path/to/more/skills"],  // 額外掃描目錄，優先序最低
    allowSymlinkTargets: ["/trusted/dir"], // 允許 symlink skill 解析的信任目錄
    watch: true                            // SKILL.md 變更時自動刷新
  },
  install: {
    preferBrew: true,          // 可用時優先使用 Homebrew
    nodeManager: "pnpm",       // npm | pnpm | yarn | bun
    allowUploadedArchives: false // 是否允許安裝私有 zip 封存
  },
  workshop: {
    autonomous: { enabled: false },  // 是否允許 agent 自主建立提案
    approvalPolicy: "auto",          // auto（agent 主動）| pending（需操作者核准）
    maxPending: 20,                  // 待處理提案上限（1–200）
    maxSkillBytes: 40000             // 提案大小上限（1024–200000 bytes）
  }
}
ℹ️ allowSymlinkTargets 值得注意：它意味著 symlink 進來的 Skill 預設不被信任，必須明確把目標目錄列為信任來源——這是防止「把一個外部目錄 link 進 skills/ 就取得執行指示權」的防線。

Skill Workshop — 讓 Agent 提案，而不是直接寫檔

產出 PROPOSAL.md，經核准才成為正式 SKILL.md
治理流程
/learnPROPOSAL.mdhash bindingskill_workshop 工具

Skill Workshop 是 OpenClaw 用來以「提案」而非「直接寫檔」方式建立與更新 workspace Skill 的受控機制。Agent 產生的內容會存成 PROPOSAL.md 草稿而不是 SKILL.md；只有在提案被套用之後，它才會成為生效的 Skill。

🔄 提案生命週期
狀態流 

pending ──→ applied      （套用，成為正式 Skill）
        ├─→ rejected     （否決）
        └─→ quarantined  （隔離）

stale    ← 30 天未使用，或目標 Skill 在套用前已被改動（hash 不符）
archived ← 90 天
✅ 四項安全設計

Hash binding：更新提案會綁定當前目標的 hash，若正式 Skill 在套用前被改動，提案自動變成 stale，避免蓋掉別人的修改。可回復：rollback 中繼資料在檔案變更之前寫入。範圍受限：只能修改 workspace Skill，永遠不會動到內建或系統 Skill。不可繞道：系統會阻止 Agent 用直接檔案操作跳過提案流程。

🖥️ 三種使用入口
chat / CLI / tool 
# 對話中
/learn   或直接請 Agent 學一個新技能

# CLI
openclaw skills workshop propose-create
openclaw skills workshop propose-update
openclaw skills workshop apply
openclaw skills workshop reject
openclaw skills workshop quarantine
openclaw skills workshop list      # 檢視 agent 提案

# Agent 工具
skill_workshop  （actions: create / revise / inspect / apply）
ℹ️ approvalPolicy 的兩種取值："auto" 讓 Agent 主動的操作略過額外詢問；"pending" 則要求操作者核准。配合 autonomous.enabled: false（預設）就能維持「Agent 可以建議，但人決定」的關係。

ClawHub 發布規範

MIT-0、50MB、禁止付費 Skill
發布生態

目錄要求：必填 SKILL.md（接受舊名 skills.md），選用支援檔案、.clawhubignore、.gitignore。發布時伺服器會從 frontmatter 擷取中繼資料，所以 name / description / version（語意化版號）必須正確。

大小限制：封裝包上限 50MB；文字分析涵蓋 SKILL.md 加上約 40 個 UTF-8 檔案（best effort）。所有檔案類型都接受，安全掃描會拿到完整封裝內容。

⚠️ 授權是 MIT-0，且不可協商。所有發布的 Skill 一律採用 MIT-0——任何人皆可使用、修改及重新散布。ClawHub 明文禁止付費 Skill、定價中繼資料與付費牆。不想被自由散布的內容就不要發上去。

要發布可安裝獨立 CLI（npm install -g clawhub），或透過 Skill Workshop 提案交由操作者審核後再實施。

撰寫最佳實務與常見錯誤

官方原則：「告訴模型要做什麼，不是怎麼當 AI」
實務建議
✅ 建立一個 Skill 的四步流程
workflow 

1. 建目錄     mkdir -p ~/.openclaw/workspace/skills/skill-name
2. 寫 SKILL.md（至少 name + description）
3. 確認載入   openclaw skills list
4. 實測       openclaw agent --message "..."
✅ 該做的

指示簡短——官方原則是「告訴模型要做什麼，不是怎麼當 AI」。description 寫觸發條件，把使用者可能說的話寫進去（含同義詞、常見說法），因為它是唯一常駐 prompt 的判斷依據。大內容外移到附帶檔案並用 {baseDir} 引用。先在本機測過再分享。

⚠️ 該避免的

使用 exec 時務必防注入——官方明確警示要避免未信任輸入造成任意命令執行。不要寫死絕對路徑（用 {baseDir}）。不要把憑證寫進 SKILL.md（用 requires.env 宣告，值從環境注入）。不要用 allow list 當安全邊界（它只是可見性過濾器）。

ℹ️ 一個判斷 Skill 該不該存在的問題：「這件事我是不是每次都要重新解釋一遍？」如果是，就該寫成 Skill；如果只是這次任務的特殊要求，寫在對話裡就好。反覆出現的流程 → Skill；一次性的規則 → prompt；永久性的權限與紅線 → AGENTS.md。
