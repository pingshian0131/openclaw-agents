💬 LINE Official Account × ngrok Webhook 建置技術報告

從零建立 LINE 官方帳號（LINE OA）與 Messaging API Channel，用 ngrok 把本機 server 暴露成 HTTPS 公開網址接收 Webhook 事件，並完成簽章驗證與回覆訊息的完整端對端流程。

LINE Messaging API LINE Official Account Manager ngrok v3 Python / FastAPI Node.js / Express HMAC-SHA256 簽章驗證
⚡

三個最容易卡住的地方，先講在前面： ①「回應模式」沒調整 —— OA Manager 的自動回應訊息還開著、Webhook 沒開，訊息永遠不會送到你的 server； ② 簽章驗證用了被框架解析過的 body（parsed JSON）而不是原始 raw bytes，導致每次都 401； ③ ngrok 免費版每次重啟網址都會變，忘了回 LINE Console 更新 Webhook URL，就會以為「昨天還好好的今天壞了」。

名詞對照表

先把 LINE 的四層概念分清楚，後面設定才不會找不到入口
ℹ️

LINE 的後台被拆成兩個網站，這是新手最大的混亂來源：developers.line.biz（開發者用：憑證、Webhook URL）與 manager.line.biz（營運用：回應模式、圖文選單、好友管理）。同一個 OA 的設定散落在兩邊，本報告會標明每一步該去哪個站。

名詞 所在後台 說明
LINE Business ID 共用 登入 LINE 商用服務的身分，可用 LINE 個人帳號或 email 註冊。建議綁 LINE 帳號，之後手機掃碼登入較方便。
Provider
（提供者）		 Developers 提供服務的主體（個人或公司）。同一個 Provider 底下的 Channel 共用同一組 userId，跨 Provider 的 userId 不同 —— 若未來要多個 bot 共用會員資料，務必放同一個 Provider。
Channel
（頻道）		 Developers 一個對外服務的技術單位。要做聊天機器人選 Messaging API 類型；要做網頁登入才選 LINE Login。
LINE Official Account
（OA／官方帳號）		 OA Manager 使用者實際加好友的那個帳號。一個 Messaging API Channel ↔ 一個 OA，一對一綁定，建立 Channel 時會自動生出對應的 OA。
Channel secret Developers 32 字元字串，用來驗證 X-Line-Signature，證明 request 真的來自 LINE。
Channel access token Developers 呼叫 Messaging API（回覆、推播、取得個人資料）用的 Bearer token。長期 token 不會自動過期，但可手動重新發行。
Webhook URL Developers LINE 主動 POST 事件過來的網址。必須是 HTTPS 且憑證有效，這是本機開發需要 ngrok 的唯一原因。
reply token — 每個 webhook event 附帶的一次性 token，用來「回覆這一則訊息」。只能用一次、約 1 分鐘內失效，過期只能改用 push message（計費）。
ngrok — 反向代理隧道服務。在本機跑一個 agent，向 ngrok 雲端註冊一個公開 HTTPS 網址，把外部流量轉進 localhost:PORT，不需要設定路由器 port forwarding，也不需要自己申請憑證。

建立步驟總覽

完整順序、每步耗時、產出物與依賴關係 —— 照這個順序做不會回頭重工
🧭

為什麼順序重要：Webhook URL 綁定（步驟 7）會立刻觸發 LINE 的 Verify 連線檢查，所以 server（步驟 5）和 ngrok（步驟 6）必須先跑起來才去填 URL；而回應模式（步驟 4）沒設好的話，步驟 8 測試時訊息會被 LINE 的自動回應攔走，你會誤判成程式有 bug。

前置需求（開始前先確認）

  • LINE 個人帳號（手機上已安裝 LINE，用來登入後台與測試加好友）
  • 一組 email（Channel 聯絡用，會收到 LINE 的通知信）
  • 本機開發環境：Python 3.9+ 或 Node.js 18+ 任一
  • ngrok 帳號（免費，取得 authtoken 必需；未登入的 ngrok 無法啟動隧道）
  • 可用的本機 port：本文範例統一用 8000

八個步驟的執行順序

Step 1 · 註冊開發者帳號　≈ 3 分鐘
登入 developers.line.biz/console，建立 LINE Business ID、填寫開發者名稱與 email。
產出：可進入 Console 的帳號。
Step 2 · 建立 Provider 與 Messaging API Channel　≈ 5 分鐘
建 Provider → 建 Channel（類型選 Messaging API）→ 系統自動生成對應的 LINE Official Account。
產出：一個 Channel + 一個 OA。⚠️ 國家/地區選錯無法修改。
Step 3 · 取得 Channel secret 與 access token　≈ 2 分鐘
Basic settings 抄 secret、Messaging API 頁發行 long-lived token，寫進 .env。
產出：LINE_CHANNEL_SECRET、LINE_CHANNEL_ACCESS_TOKEN。
Step 4 · 設定 OA 回應模式　≈ 3 分鐘
到 OA Manager 開啟 Webhook、關閉 自動回應訊息。
產出：訊息事件會真的往 webhook 送。⚠️ 漏掉這步後面全部白做。
Step 5 · 撰寫並啟動本機 Webhook Server　≈ 15 分鐘
實作 POST /webhook：驗簽 → 立刻回 200 → 處理事件 → 呼叫 Reply API。
產出：http://localhost:8000/webhook 可用。
Step 6 · 安裝並啟動 ngrok　≈ 5 分鐘
安裝 → ngrok config add-authtoken → ngrok http 8000，取得 https://xxxx.ngrok-free.app。
產出：公開 HTTPS 網址 + 127.0.0.1:4040 檢視器。
Step 7 · 綁定 Webhook URL 並 Verify　≈ 2 分鐘
Console 填入 https://xxxx.ngrok-free.app/webhook → 開啟 Use webhook → 按 Verify 應顯示 Success。
產出：LINE ↔ 本機通道打通。
Step 8 · 端對端測試與觀測　≈ 10 分鐘
掃 QR 加好友（follow 事件）→ 傳文字（message 事件）→ 在 ngrok Inspector 與 server log 對照 request/response。
產出：bot 會回話。

依賴關係速查

步驟 必須先完成 若跳過會發生什麼
1 → 2—沒帳號無法進 Console。

1

註冊開發者帳號（LINE Business ID）

developers.line.biz/console → 建立開發者身分

操作步驟

  1. 瀏覽器開啟 LINE Developers Console：https://developers.line.biz/console/

  2. 點右上角 Log in，選擇登入方式：
    · Log in with LINE account（推薦）—— 用手機 LINE 掃 QR 或輸入 email/密碼；
    · Log in with business account —— 用 LINE Business ID 專用 email。

  3. 首次登入會要求建立開發者帳號，填入 Developer name（會顯示在 Console，可用暱稱）與 Your email（接收 LINE 的技術通知，例如 token 異常、webhook 錯誤率上升）。

  4. 勾選同意 LINE Developers Agreement，送出後即進入 Console 首頁。

💡

用哪個 LINE 帳號登入很重要。登入的帳號會成為這個 OA 的管理者（Admin）。若這是公司專案，建議用公司共用帳號建立，之後再從 OA Manager 的「權限管理」邀請同事，避免離職時整個 OA 被鎖住。

⚠️

手機 LINE 需先在「設定 → 我的帳號」啟用 email 登入，否則 Console 的 email 登入方式會顯示帳號不存在。掃 QR 登入不受此限。

2

建立 Provider 與 Messaging API Channel

建立 Channel 的同時，LINE 會自動幫你生出一個對應的官方帳號（OA）

2-1　建立 Provider

  1. Console 首頁 → Create a new provider。

  2. 填入 Provider name（例如公司名或個人品牌名，1–100 字元）。

  3. 按 Create。

⚠️

Provider name 會對使用者顯示（例如 LINE Login 的同意畫面上會出現「〇〇 想要存取…」），不要填 test、abc 這種暫用名稱。同一個 Provider 底下的所有 Channel 共用同一組 userId，未來要多 bot 共用會員請放在一起。

2-2　建立 Messaging API Channel

  1. 進入剛建立的 Provider → Channels 分頁 → Create a Messaging API channel。

  2. 依序填寫下表欄位。

  3. 勾選同意 LINE Official Account Terms of Use 與 LINE Official Account API Terms of Use，按 Create。

  4. 建立完成後，Console 會提示已同步建立一個 LINE Official Account，可從 manager.line.biz 看到它。

欄位填寫說明

欄位 可否修改 說明與注意事項
Company or owner's country or region 不可修改 決定費率方案、可用功能與帳務地區。台灣專案請選 Taiwan。選錯只能刪掉 Channel 重建（連 OA 一起刪）。
Channel name 可 即 OA 的顯示名稱（使用者看到的名字）。不可包含「LINE」字樣，也不可用容易誤認為官方的名稱，否則審核會被退。建立後 7 天內不可再改名。
Channel description 可 服務說明，會顯示在 OA 的個人檔案頁。
Channel icon 可 頭像圖（建議 ≥ 640×640 px，JPG/PNG，3 MB 以內）。可先留空，之後在 OA Manager 補。
Category / Subcategory 可 產業分類，影響 OA 在 LINE 內的搜尋與推薦。開發測試可選「個人 → 其他」。
Email address 可 LINE 用來聯絡你的信箱，重要通知（webhook 錯誤率、政策變更）會寄到這裡。
Privacy policy URL / Terms of use URL 可 選填。若要送審綠盾認證或使用部分進階功能會需要。

另一條路：先建 OA 再啟用 Messaging API

兩種路徑最終得到的東西完全一樣，差別只在入口。如果 OA 已經由行銷同事建好了，就走右邊那條。

比較項 路徑 A：從 Developers Console 建 路徑 B：從 OA Manager 建
入口 developers.line.biz/console → Create a Messaging API channel manager.line.biz → 建立帳號 → 設定 → Messaging API → 啟用
適合情境 開發者自己從零開始，最短路徑。 OA 已存在（行銷已在經營、已有好友），要加掛程式功能。
需要指定 Provider 建立時就選 啟用 Messaging API 時再選或新建
結果 都會得到「1 個 Messaging API Channel + 1 個 OA」的一對一綁定，憑證都在 Developers Console 拿。
ℹ️

關於費用：建立 OA 與 Channel 本身免費，開發期完全不會產生費用。回覆訊息（reply message）不計入訊息額度，只有主動推播（push / broadcast / multicast）才計費，免費方案有每月則數上限（依地區方案而異）。所以做 bot 開發測試幾乎不會超額。

4

設定 OA 回應模式（決定 webhook 收不收得到）

manager.line.biz → 設定 → 回應設定 · 這一步漏掉，後面全部白做
🚨

OA 預設是「自動回應模式」。在這個狀態下，使用者傳訊息只會收到 LINE 內建的罐頭回覆，事件不會送到你的 webhook。這是「程式明明沒錯卻收不到任何 request」最常見的原因。

4-1　進入 OA Manager 的兩種方式

  • 從 Console 跳轉：Channel → Messaging API 分頁 → 找到 Auto-reply messages 或 Greeting messages 旁的 Edit，會直接開啟對應的 OA Manager 設定頁。
  • 直接前往：開啟 https://manager.line.biz/ → 選擇你的帳號 → 右上 設定（Settings） → 左側 回應設定（Response settings）。

4-2　三個開關該怎麼設

項目 Bot 開發設定 說明
Webhook 開啟 ✅ 唯一讓事件流向你的 server 的開關。這個關著，Console 那邊的 Webhook URL 填得再正確都沒用。
自動回應訊息
Auto-reply messages		 關閉 ❌ 開著的話 LINE 會先用內建罐頭訊息回覆使用者，造成「使用者同時收到罐頭訊息 + 你的 bot 回覆」的雙重回應。
加入好友的歡迎訊息
Greeting messages		 視需求 若你打算用程式在 follow 事件自己發歡迎訊息，這裡請關閉避免重複；若懶得寫程式就留著用內建的。
聊天 / Chat 視需求 開啟後真人可在 OA Manager 的聊天室介面手動回覆。注意：手動聊天模式下部分事件仍會送 webhook，但真人與 bot 可能互相干擾，純 bot 專案建議先關閉。

🕐

5

撰寫本機 Webhook Server

三個硬性要求：驗證簽章、3 秒內回 200、用 reply token 回覆

5-0　Webhook endpoint 的合約

要求細節
HTTP method只需支援 POST。LINE 不會發 GET（你自己用瀏覽器打會 405，那是正常的）。
回應狀態碼必須是 200。非 2xx 會被記為 webhook 失敗，錯誤率過高 LINE 會寄警告信。
回應時間建議 1 秒內、最遲不超過數秒。慢的工作（打外部 API、寫 DB、跑 LLM）要丟到背景處理，先回 200。
簽章驗證比對 X-Line-Signature header：以 Channel secret 為 key、對 raw request body 做 HMAC-SHA256，再 Base64。不符請回 400。
重試與重複LINE 可能重送同一事件。用 webhookEventId 做幂等去重（記錄已處理過的 id）。
驗證用空請求按 Console 的 Verify 或 LINE 定期健康檢查時，會送 "events": [] 的空事件 POST，必須也回 200。

常見的 event.type：message（收到訊息）、follow（被加好友）、unfollow（被封鎖，沒有 replyToken）、join / leave（加入/離開群組）、postback（點按鈕）。

5-2　Python（FastAPI）—— 不依賴 SDK 的最小可用版

main.py 
# pip install fastapi "uvicorn[standard]" httpx python-dotenv
import base64, hashlib, hmac, os, asyncio, logging

import httpx
from dotenv import load_dotenv
from fastapi import FastAPI, Request, Response, HTTPException

load_dotenv()
CHANNEL_SECRET = os.environ["LINE_CHANNEL_SECRET"]
ACCESS_TOKEN   = os.environ["LINE_CHANNEL_ACCESS_TOKEN"]
REPLY_URL      = "https://api.line.me/v2/bot/message/reply"

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("line-bot")
app = FastAPI()
seen_event_ids: set[str] = set()   # 幂等去重（正式環境請換 Redis）


def verify_signature(raw_body: bytes, signature: str | None) -> bool:
    """以 channel secret 對 raw body 做 HMAC-SHA256 後 Base64，與 header 比對。"""
    if not signature:
        return False
    mac = hmac.new(CHANNEL_SECRET.encode("utf-8"), raw_body, hashlib.sha256)
    expected = base64.b64encode(mac.digest()).decode("utf-8")
    return hmac.compare_digest(expected, signature)   # 定時比較，防時序攻擊


async def reply_text(reply_token: str, text: str) -> None:
    headers = {
        "Authorization": f"Bearer {ACCESS_TOKEN}",
        "Content-Type": "application/json",
    }
    payload = {
        "replyToken": reply_token,
        "messages": [{"type": "text", "text": text[:5000]}],
    }
    async with httpx.AsyncClient(timeout=10) as client:
        r = await client.post(REPLY_URL, headers=headers, json=payload)
        if r.status_code != 200:
            log.error("reply failed %s %s", r.status_code, r.text)


async def handle_event(event: dict) -> None:
    """所有耗時邏輯都放這裡，在回 200 之後才執行。"""
    event_id = event.get("webhookEventId")
    if event_id in seen_event_ids:
        log.info("duplicate event skipped: %s", event_id)
        return
    seen_event_ids.add(event_id)

    etype = event.get("type")
    token = event.get("replyToken")

    if etype == "follow" and token:
        await reply_text(token, "感謝加入！輸入任何文字我都會回你。")

    elif etype == "message" and token:
        msg = event["message"]
        if msg["type"] == "text":
            await reply_text(token, f"你說的是：{msg['text']}")
        else:
            await reply_text(token, f"收到 {msg['type']} 類型的訊息")

    elif etype == "unfollow":
        log.info("user blocked: %s", event["source"].get("userId"))   # 無 replyToken，不能回訊息


@app.post("/webhook")
async def webhook(request: Request):
    raw = await request.body()                       # ← 必須是 raw bytes，不能用 parsed json 再 dumps
    signature = request.headers.get("X-Line-Signature")

    if not verify_signature(raw, signature):
        log.warning("invalid signature")
        raise HTTPException(status_code=400, detail="invalid signature")

    body = await request.json()
    events = body.get("events", [])
    log.info("received %d event(s)", len(events))     # Verify 時會是 0，屬正常

    for ev in events:                                 # 丟背景跑，立刻回 200
        asyncio.create_task(handle_event(ev))

    return Response(status_code=200)

server.js 
// npm i express dotenv
require('dotenv').config()
const express = require('express')
const crypto  = require('crypto')

const { LINE_CHANNEL_SECRET: SECRET, LINE_CHANNEL_ACCESS_TOKEN: TOKEN } = process.env
const app = express()
const seen = new Set()

// 關鍵：用 raw body parser，把原始 bytes 留在 req.body 供驗簽使用
app.post('/webhook', express.raw({ type: '*/*' }), (req, res) => {
  const signature = req.get('X-Line-Signature') || ''
  const expected  = crypto
    .createHmac('SHA256', SECRET)
    .update(req.body)                 // Buffer，不是字串
    .digest('base64')

  const ok = signature.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expected))
  if (!ok) return res.status(400).send('invalid signature')

  const body = JSON.parse(req.body.toString('utf8'))
  res.sendStatus(200)                    // 先回 200，再處理

  for (const ev of body.events ?? []) {
    if (seen.has(ev.webhookEventId)) continue
    seen.add(ev.webhookEventId)
    handleEvent(ev).catch(err => console.error('handleEvent failed', err))
  }
})

async function handleEvent(ev) {
  if (ev.type === 'message' && ev.message.type === 'text') {
    await replyText(ev.replyToken, `你說的是：${ev.message.text}`)
  } else if (ev.type === 'follow') {
    await replyText(ev.replyToken, '感謝加入！')
  }
}

async function replyText(replyToken, text) {
  const r = await fetch('https://api.line.me/v2/bot/message/reply', {
    method:  'POST',
    headers: {
      'Content-Type':  'application/json',
      'Authorization': `Bearer ${TOKEN}`,
    },
    body: JSON.stringify({ replyToken, messages: [{ type: 'text', text }] }),
  })
  if (!r.ok) console.error('reply failed', r.status, await r.text())
}

app.get('/healthz', (_, res) => res.json({ ok: true }))
app.listen(8000, () => console.log('listening on :8000'))

5-4　用官方 SDK 的簡化版（驗簽由 SDK 處理）

官方 SDK 會幫你做簽章驗證與型別轉換，程式碼短很多；缺點是把細節藏起來，出錯時較難定位。建議先手寫一次理解原理，再換 SDK。

# pip install line-bot-sdk flask
from flask import Flask, request, abort
from linebot.v3 import WebhookHandler
from linebot.v3.exceptions import InvalidSignatureError
from linebot.v3.messaging import (
    Configuration, ApiClient, MessagingApi, ReplyMessageRequest, TextMessage,
)
from linebot.v3.webhooks import MessageEvent, TextMessageContent

app     = Flask(__name__)
handler = WebhookHandler(CHANNEL_SECRET)
config  = Configuration(access_token=ACCESS_TOKEN)

@app.route("/webhook", methods=["POST"])
def webhook():
    signature = request.headers["X-Line-Signature"]
    body      = request.get_data(as_text=True)
    try:
        handler.handle(body, signature)     # SDK 內部完成驗簽 + 路由到 handler
    except InvalidSignatureError:
        abort(400)
    return "OK"

@handler.add(MessageEvent, message=TextMessageContent)
def on_text(event):
    with ApiClient(config) as client:
        MessagingApi(client).reply_message(
            ReplyMessageRequest(
                reply_token=event.reply_token,
                messages=[TextMessage(text=f"你說的是：{event.message.text}")],
            )
        )
🔑

驗簽失敗 99% 是 raw body 問題。如果你先讓框架把 JSON 解析成物件、再 json.dumps() 回字串來驗簽，空白、鍵順序、Unicode escape 都會不一樣，HMAC 必然對不上。一定要拿到未經任何處理的原始 bytes。Express 尤其容易踩到 —— 若全域掛了 express.json()，記得讓 /webhook 走 express.raw()。

安裝並啟動 ngrok

把 localhost:8000 變成 LINE 打得到的公開 HTTPS 網址

6-0　為什麼需要 ngrok

LINE Platform 的 webhook 是由 LINE 主動連進來的，它必須能從公網解析並連上你的 URL，而且只接受有效憑證的 HTTPS。本機 localhost:8000 在公網上不存在、也沒有憑證。ngrok 在本機跑一個 agent 與雲端建立反向隧道，替你提供公開網域與有效 TLS 憑證，流量從 ngrok Edge 經隧道送進你的 localhost —— 不必動路由器、不必申請憑證、不必部署。

替代方案差異
Cloudflare Tunnel
cloudflared		免費、可綁自有網域、無隨機網址問題，但需 Cloudflare 帳號與網域設定，起步稍複雜。
VS Code Port Forwarding內建於 VS Code / GitHub Codespaces，需將可見性設為 Public，否則外部會被導向登入頁。
localtunnel / bore更輕量，但穩定性與觀測工具不如 ngrok。
直接部署到雲端最接近正式環境，但每次改程式都要重新部署，開發迭代慢。

綁定 Webhook URL 並執行 Verify

Developers Console → Messaging API → Webhook settings
✅

執行前確認兩件事：① 本機 server 已啟動（curl http://localhost:8000/healthz 有回應）；② ngrok 隧道 online（瀏覽器開 https://xxxx.ngrok-free.app/healthz 看得到 JSON）。兩者都通，Verify 才會成功。

操作步驟

  1. Console → 你的 Channel → Messaging API 分頁。

  2. 找到 Webhook settings 區塊 → Webhook URL 右側 Edit。

  3. 填入完整網址，含路徑：https://a1b2-c3d4-e5f6.ngrok-free.app/webhook，按 Update。

  4. 把 Use webhook 開關切為開啟。（這個開關與 OA Manager 的 Webhook 設定連動。）

  5. 按 Verify。畫面應顯示 Success；同時你的 server log 會出現一筆 received 0 event(s)，ngrok 檢視器出現一筆 POST /webhook 200 OK。

  6. （選用）開啟 Error statistics 觀察，以及 Webhook redelivery（失敗自動重送，配合幂等去重使用）。

Verify 送的是什麼

Verify 會發一個合法簽章、但事件清單為空的 POST。你的程式必須通過驗簽並回 200：

{ "destination": "Uxxxxxxxx...", "events": [] }

如果你的程式碼寫成「events 為空就 raise / 回 400」，Verify 就會失敗。空事件是正常流量，必須容忍。

Verify 失敗對照表

Console 顯示最可能原因處理方式
An error occurred while connecting ngrok 沒開、隧道已斷、或網址過期（重啟換了網址）。 重新啟動 ngrok，抄新網址回填；改用靜態網域可根治。
502 Bad Gateway 隧道通了但本機沒服務在聽，或 ngrok 指到錯誤的 port。 確認 server 有跑、port 與 ngrok http PORT 一致。
404 Not Found 路徑寫錯（少了 /webhook、或程式註冊的是 /callback）。 對齊程式的 route 與 Console 填的路徑。
400 Bad Request 驗簽失敗（raw body 問題、secret 貼錯或多了空白），或程式對空 events 直接報錯。 先在驗簽前印出 raw body 長度與 header，再逐項核對；容忍空 events。
405 Method Not Allowed endpoint 只註冊了 GET。 改為 POST（或同時支援）。
Timeout / 很久才失敗 handler 同步做了慢事情（打 API、跑模型）才回應。 改成「先回 200，再背景處理」。
Verify 成功但實際傳訊息沒反應 通道沒問題，是回應模式沒設好（見步驟 4）。 OA Manager 開 Webhook、關自動回應訊息。

8-1　測試流程

① 掃 QR 加好友 → 預期收到 follow 事件
Console 的 Messaging API 分頁有 QR code，用手機 LINE 掃描並加入。server log 應出現 received 1 event(s) 與 type: follow。
② 在聊天室傳「hello」→ 預期收到 message 事件並得到回覆

③ 打開 ngrok 檢視器 http://127.0.0.1:4040
可以看到每一筆 request 的完整 headers、body、你的回應狀態碼與耗時。Replay 按鈕能重送同一筆 request，改完程式不必再回手機重打字，這是整套流程裡最省時間的工具。
④ 傳貼圖 / 圖片 / 位置 → 確認非文字訊息不會讓程式爆掉

unfollow 事件沒有 replyToken，若程式照樣呼叫 Reply API 會 400。測試完記得解除封鎖。

8-3　不靠手機測試：自己產生合法簽章打 curl

手動 curl 時簽章不會自動生成，直接打會被自己的驗簽擋掉（這代表驗簽有效）。下列腳本用 channel secret 產生正確簽章，可在完全不碰手機的情況下測 endpoint：

test_webhook.sh 
#!/usr/bin/env bash
set -euo pipefail
source .env

BODY='{"destination":"Utest","events":[{"type":"message","webhookEventId":"evt-local-001","deliveryContext":{"isRedelivery":false},"timestamp":1755000000000,"source":{"type":"user","userId":"Ulocaltest"},"replyToken":"dummy-reply-token","mode":"active","message":{"type":"text","id":"1","text":"hello from curl"}}]}'

# 用 channel secret 對 body 做 HMAC-SHA256 再 Base64
SIG=$(printf '%s' "$BODY" \
  | openssl dgst -sha256 -hmac "$LINE_CHANNEL_SECRET" -binary \
  | openssl base64)

curl -i -X POST http://localhost:8000/webhook \
  -H "Content-Type: application/json" \
  -H "X-Line-Signature: $SIG" \
  --data-raw "$BODY"
💡

預期得到 HTTP/1.1 200 OK。因為 replyToken 是假的，Reply API 那一段會在 log 印出 400 Invalid reply token —— 這是正常的，代表驗簽與事件路由都正確，只有回覆那步因假 token 失敗。要驗證回覆功能請用真手機或 ngrok 的 Replay。

# tests/test_signature.py
import base64, hashlib, hmac
from main import verify_signature, CHANNEL_SECRET


def sign(body: bytes) -> str:
    mac = hmac.new(CHANNEL_SECRET.encode(), body, hashlib.sha256)
    return base64.b64encode(mac.digest()).decode()


def test_valid_signature():
    body = b'{"events":[]}'
    assert verify_signature(body, sign(body)) is True


def test_tampered_body_rejected():
    body = b'{"events":[]}'
    assert verify_signature(b'{"events":[1]}', sign(body)) is False


def test_missing_signature_rejected():
    assert verify_signature(b'{}', None) is False

疑難排解對照表

依「症狀」查，先看該從哪個觀測點下手
症狀 原因 解法
傳訊息只收到 LINE 的罐頭回覆，webhook 完全沒被打 OA 仍在自動回應模式，或 Webhook 開關關著。 OA Manager → 回應設定：Webhook 開、自動回應訊息 關。改完等 1 分鐘再測。
使用者收到兩則回覆（罐頭 + bot） 自動回應訊息與 webhook 同時啟用。 關閉自動回應訊息與歡迎訊息，改由程式在 follow 事件自行回覆。
每一筆 request 都 400 invalid signature 用了 parsed body 而非 raw bytes；或 secret 複製時多了空白／換行；或用了 access token 當 secret。 改讀 raw bytes；len(CHANNEL_SECRET) 應為 32；secret 在 Basic settings、token 在 Messaging API，別拿錯。
ngrok 檢視器有 request，但 server log 沒動靜 ngrok 指到的 port 不是 server 監聽的 port，或 server 綁在 127.0.0.1 而容器/VM 隔離。 核對 port；容器內請綁 0.0.0.0。檢視器會顯示 502 佐證。
Reply API 回 400 Invalid reply token replyToken 已用過、已過期（約 1 分鐘），或事件本來就沒有 token（如 unfollow）。 一個 token 只回一次；慢流程改用 push message；處理事件前先檢查 replyToken 存在。
Reply API 回 401 Unauthorized access token 錯、過期、被 Reissue 換掉，或 header 少了 Bearer 前綴。 重新發行 token 並更新 .env；確認格式為 Authorization: Bearer <token>。
Reply API 回 403 Forbidden 方案不支援該功能，或 token 屬於另一個 Channel。 確認 token 與目標 OA 是同一個 Channel。
Reply API 回 429 Too Many Requests 觸發速率限制或訊息額度用盡（push 類）。 加退避重試；reply 不計額度，改用 reply 為主。
同一則訊息被處理兩次（回覆兩次或資料重複寫入） LINE 重送事件（deliveryContext.isRedelivery = true），或你回 200 太慢導致 LINE 判定失敗而重試。 用 webhookEventId 做幂等去重；加快回 200 的速度。
昨天可以、今天全部失敗 ngrok 重啟換了網址（未用靜態網域），Console 裡的 URL 已失效。 改用靜態網域 --url=；或寫個腳本啟動時自動抓網址提醒自己更新。
瀏覽器開 ngrok 網址看到 ngrok 警告頁 免費版對瀏覽器 GET 的攔截頁。 正常現象，不影響 LINE 的 POST。要繞過可帶 ngrok-skip-browser-warning header。
Console 顯示 webhook 錯誤率升高但現在測都正常 隧道曾中斷（電腦睡眠、網路切換、免費版 session 逾時）。 開發環境可忽略；正式環境請部署到固定主機，不要用 ngrok。
ngrok: command not found 未安裝或不在 PATH。 重裝，或用完整路徑執行；npm 全域安裝需確認 npm bin -g 在 PATH。
ngrok 報 authentication failed 未設定 authtoken 或 token 失效。 重跑 ngrok config add-authtoken <token>。
ngrok 報 address already in use / 4040 佔用 已有一個 ngrok 在跑。 關掉舊的（pkill ngrok），或用 --inspect=false。

安全與上線注意事項

ngrok 是開發工具，不是部署方案

開發期就該做對的事

  • 簽章驗證絕不可略過。ngrok 網址是公開的，沒驗簽等於任何人都能偽造 LINE 事件呼叫你的服務。用 hmac.compare_digest / timingSafeEqual 做定時比較。
  • secret 與 token 只放環境變數。.env 進 .gitignore，另備一份 .env.example。不慎外洩就立刻 Reissue。
  • 先回 200，再做事。耗時工作丟背景（asyncio task、Celery、queue），避免 LINE 判定超時而重送。
  • 幂等處理。以 webhookEventId 去重，並檢查 deliveryContext.isRedelivery。開發用 in-memory set 可以，正式請用 Redis 或 DB 唯一索引。
  • log 不要印出完整 token / 使用者個資。需要時只印前後 4 碼。
  • 開發完關掉 ngrok。不要讓隧道整夜掛著。

多人協作的常見衝突：一個 Channel 只能設定一個 Webhook URL。兩個開發者同時各開自己的 ngrok，會互相把對方的 URL 蓋掉。解法是每人建立自己的測試 Channel + 測試 OA（免費），共用的 Channel 只指向 staging 環境。
