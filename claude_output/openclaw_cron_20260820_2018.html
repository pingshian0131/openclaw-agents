Cron 是什麼 — 跑在 gateway 裡的內建排程器

存工作、按時喚醒 Agent、把輸出路由到頻道／webhook／或哪裡都不去
基礎架構
gateway processSQLite 持久化重啟後仍存活

Cron 是 OpenClaw 內建的排程器：它負責儲存工作、在指定時間喚醒 Agent，並把輸出路由到聊天頻道、webhook，或不送任何地方。

⚠️ 最重要的一件事：排程器跑在 gateway 行程裡，不在模型裡。所以 gateway 必須持續運行，排程才會觸發。筆電闔上、gateway 沒起來 = 排程不會跑。

工作定義、待執行狀態與執行歷史都持久化在 SQLite，因此排程能跨 gateway 重啟存活。舊版的 JSON 檔會被遷移一次，並改名加上 .migrated 後綴。

五種排程種類

不只有 cron 運算式 — 還有一次性、固定間隔、以及兩種事件觸發
核心排程
種類旗標說明
at--at一次性時間點（ISO 8601，或相對時間如 20m）
every--every固定間隔（10m、1h、1d）
cron--cron5 或 6 欄位 cron 運算式，可搭 --tz
on-exit--on-exit事件觸發：被監看的命令結束時觸發一次
stream--stream-command事件觸發：由受監督的長時間執行命令產生的批次行觸發
ℹ️ on-exit 與 stream 常被忽略，但它們把 cron 從「時鐘」變成「事件系統」——例如監看一個長時間跑的 build，結束時自動觸發一輪 Agent 分析。stream 需要 cron.triggers.enabled: true 才能用（見安全章節）。
⚠️ Stream 排程若在 60 秒內連續失敗 5 次，會維持錯誤狀態直到手動重新啟用——它不會自己無限重試。
3

時區規則與 top-of-hour 抖動

兩個預設值會讓人踩坑：UTC 與 0–5 分鐘隨機偏移
易踩雷時間
⚠️ 時區的三條規則

① 沒帶時區的時間戳一律視為 UTC。寫 --at "2027-02-01T16:00:00" 而心裡想的是台北時間 → 會差 8 小時。
② 要用當地時間解讀日期，得明確加 --tz（IANA 時區名，例如 --tz America/New_York、--tz Asia/Taipei）。
③ 沒有 --tz 的 cron 運算式，使用 gateway 主機的時區——注意這和 at 的預設（UTC）不一致。

🎲 整點抖動（staggering）

針對整點的 cron 運算式，系統會加上 0–5 分鐘的隨機偏移，避免大量工作在同一秒擠在一起。若你需要精準在整點執行，加 --exact。

ℹ️ 所以「我設 0 7 * * * 但它 7:03 才跑」不是 bug，是刻意的分散設計。真的要精確就用 --exact。

四種 payload — 一個工作只能有一種

要不要花模型的錢，取決於你選哪一種
核心執行
Payload旗標執行方式會呼叫模型？
系統事件--system-event <text>排入主要 session 的事件佇列✘ 不呼叫
Agent 訊息--message <text>由模型驅動的 Agent 輪次✔ 會
命令--command <shell>在 gateway 主機執行 shell／行程✘ 不呼叫
腳本--script <file｜->無介面 code mode，使用 Agent 工具部分
ℹ️ 選型建議：單純提醒自己 → --system-event（零模型成本，只是把事件排進主 session）。需要判斷與寫作（每日摘要、報告）→ --message。純機械動作（備份、清檔、跑腳本）→ --command。要用 Agent 工具但不需要對話 → --script。
5

Session 模式 — 這個工作在哪個對話脈絡裡執行

main / isolated / current / session:<id>
重要脈絡

main：把系統事件排進排程的喚醒頻道，適合提醒類工作。
isolated：專屬的 Agent 輪次、全新 session，每次執行都重設對話脈絡——適合報告與背景任務，也是 cron create 的預設。
current：綁定建立這個工作時的互動 session 脈絡。
session:<id>（自訂）：跨多次執行保留脈絡，適合每日 standup 這類需要記得上次講到哪的流程。

ℹ️ 成本與品質的權衡：isolated 每次從零開始 → 便宜、可預測，但不知道上下文；session:<id> 有連續性 → 能接續，但 context 會隨時間變長。日報用 isolated，多輪推進的專案追蹤用自訂 session。

傳遞與路由 — 結果送到哪裡去

announce / webhook / none，以及 NO_REPLY 的抑制行為
實務傳遞
傳遞旗標 

--announce           # 若 Agent 自己沒送訊息，備援傳送到目標頻道
--webhook <url>      # 把完成 payload POST 到 HTTP 端點
--none               # 不做 executor 層級的備援傳遞
--no-deliver         # 停用傳送

# 指定目標
--channel slack     --to "channel:C123"
--channel telegram  --to "-1001234567890"
--thread-id <id>    --account <acct>

隔離式的 cron add 工作預設使用 --announce 傳送。announce 模式會先嘗試直接發訊息，失敗才退回 executor 層級的通知。

🔗 Webhook 驗證

兩種擇一：Authorization: Bearer <token>（建議）或 x-openclaw-token: <token>。放在 query string 的權杖會被拒絕。內建端點：POST /hooks/wake（把系統事件排入主 session）、POST /hooks/agent（執行隔離 Agent 輪次）、POST /hooks/<name>（自訂對應鉤子）。

⚠️ 沒收到訊息的五個常見原因

① 傳遞模式是 none——這是預期行為（Agent 仍可自己用 message 工具送）。② channel／to 未設或無效 → 直接略過傳送。③ Matrix 聊天室 ID 區分大小寫，要用 !room:server 或 room:!room:server 格式。④ 回傳 unauthorized／Forbidden → 傳遞被阻擋。⑤ 隔離執行回傳 NO_REPLY 時，OpenClaw 會抑制對外傳遞——這常是「明明跑成功卻沒收到通知」的答案。

openclaw cron CLI 總覽

十個子命令，以及最常用的旗標
參考CLI
✅ 上手三個範例
基本用法 
# 一次性提醒（不呼叫模型，只排入主 session）
openclaw cron add --name "Reminder" --at "2027-02-01T16:00:00Z" \
  --session main --system-event "Check the draft" --wake now

# 每天早上七點的隔離式摘要
openclaw cron create "0 7 * * *" "Summarize overnight updates." \
  --name "Morning brief" --tz "America/Los_Angeles" --session isolated

# 查看、強制執行、看歷史
openclaw cron list
openclaw cron run <jobId>
openclaw cron runs --id <jobId> --limit 50

🗒️ scratch — 被低估的功能

每個排程工作可以維護一份持久暫存文件（上限 256 KiB），它會被附加到 prompt，作為輕量的檢查點清單，讓工作不必在每次執行之間重複處理舊項目。

CLI 

openclaw cron scratch <jobId> --set "checklist content"
openclaw cron scratch <jobId> --file ./checklist.md
openclaw cron scratch <jobId> --unset
ℹ️ 這解決了 isolated session 的核心弱點：每次都全新開始，就不知道上次處理到哪。scratch 給了一個「只保留結論、不保留整段對話」的中間選項——比自訂 session 便宜，又比純 isolated 有記憶。

設定欄位

cron 命名空間下的關鍵設定
參考設定
~/.openclaw/openclaw.json 

{
  cron: {
    enabled: true,                        // 總開關
    store: "~/.openclaw/cron/jobs.json",  // 工作儲存位置
    triggers: { enabled: false },         // 條件觸發腳本／stream（預設關，見安全章節）
    webhookToken: "replace-with-token",   // webhook 驗證權杖
    sessionRetention: "24h"               // session 保留時間
  }
}
⚠️ 環境變數 OPENCLAW_SKIP_CRON 會讓排程整體不執行。排錯時除了看 cron.enabled，也要確認這個變數沒被設定。

Cron vs Heartbeat — 該用哪一個

精確時間 vs 完整脈絡；而且 heartbeat 其實跑在 cron 上
決策對比
面向排程工作（Cron）心跳偵測（Heartbeat）
時間精準度精確（運算式／一次性）近似（預設 30 分鐘）
執行脈絡隔離或共享，可選完整的主 session 脈絡
任務紀錄（task record）一律建立從不建立
典型用途日報、一次性提醒、背景工作收信匣巡檢、行事曆檢視

選擇原則：需要精確時間的報告與背景工作 → 排程工作；受益於完整 session 脈絡、時間不必精準的監看 → 心跳偵測。

🔗 兩者其實是連動的

心跳偵測是由系統擁有的排程器工作來執行的 —— 這帶來一個實務結論：若 cron.enabled: false，心跳也會一起停止執行。

heartbeat 設定 

agents: {
  defaults: {
    heartbeat: {
      every: "30m",           // 預設 30m（OAuth／token 認證時為 1h）
      target: "last",
      isolatedSession: true,  // 大幅降低成本（見下）
      lightContext: true
    }
  }
}
ℹ️ 成本差距很誇張：官方指出使用 isolatedSession: true 可讓每次心跳的 token 消耗從約 100K 降到 2–5K（因為不帶完整對話歷史）。回應約定是：無事時回 HEARTBEAT_OK，有事則用 heartbeat_respond 帶警示內容；預設會抑制 OK、只顯示警示。若三個可見性旗標全為 false，執行會直接略過。

背景任務帳本 — cron 跑了什麼，去哪裡看

tasks 是「紀錄」不是「排程器」
觀測工具

背景任務追蹤的是在主要對話 session 之外執行的工作：ACP 執行、子代理生成、所有排程工作的執行、CLI 發起的操作、以及 session 型的媒體生成。官方強調 tasks 是日誌，不是排程器——它記錄發生了什麼與何時，何時該跑則由 cron 與 heartbeat 決定。

生命週期與指令 

queued → running → terminal (succeeded / failed / timed_out / cancelled / lost)

openclaw tasks list            # 列出（可篩選）
openclaw tasks show <lookup>   # 完整細節
openclaw tasks cancel <lookup> # 中止進行中的任務
openclaw tasks audit           # 健康檢查，回報問題
/tasks                         # 對話中的面板：本 session 相關的背景工作

保留期：終端狀態的任務紀錄保留 7 天（lost 為 24 小時）後自動刪除；自動維護每 60 秒執行一次（對帳、session 修復、標記清理與修剪）。

⚠️ 一般互動對話與心跳輪次不會建立 task 紀錄。所以 tasks list 看不到心跳——要查心跳得看 log，這也是上一節「心跳從不建立任務紀錄」的另一面。

重試、逾時與預算上限

指數退避、各種 timeout 的實際數字
維運限制
🔁 重試與退避

單次工作：暫時性錯誤（速率限制、網路、逾時）採用內建重試排程；永久性錯誤會立即停用該工作。
週期性工作：連續執行錯誤採指數退避 30 秒 → 1 分 → 5 分 → 15 分 → 60 分，下次成功執行後重設。系統會把「略過（skipped）」與「錯誤」分開統計。

⏱️ 逾時與預算（官方數字）
限制一覽 

隔離 Agent 輪次逾時    預設 60 分鐘（監控逾時優先於底層 agent 逾時）
命令型工作逾時         預設 10 分鐘
觸發腳本預算           30 秒實際經過時間，最多 5 次工具呼叫
腳本 payload           最多 300 秒（可設至上限 900 秒），
                       50 次工具呼叫預算（上限 200）
狀態儲存               單筆上限 16 KB；失敗的執行不會保存回傳狀態
scratch 文件           上限 256 KiB
ℹ️ 一次性工作的清理行為：--at 建立的工作在成功後會自動刪除，除非加上 --keep-after-run。所以「我的提醒跑完就不見了」是正常的。

安全紅線 — cron.triggers 等同無人值守的 exec

這是整份文件語氣最重的一段警告
高風險安全
⚠️ 啟用 cron.triggers.enabled: true 之後，條件觸發腳本與腳本承載內容可在無介面模式下使用所屬 Agent 的完整工具政策，包括 exec。官方要求把這視為「以該 Agent 權限進行的無人值守程式碼執行」——除非所有獲准建立排程工作的 Agent 都同樣可信，否則應保持停用。

值得拆開想的是這句話的完整含義：風險不只是「腳本會執行」，而是任何能建立排程工作的 Agent，都獲得了一條在無人看管時間點、以自身完整權限執行程式碼的路徑。多 Agent 環境下，這等於把信任邊界從「單一 Agent」擴大到「所有能排程的 Agent 集合」。

✅ 其他安全實務

Webhook 權杖：用 Authorization: Bearer（建議）或 x-openclaw-token，query string 權杖會被拒絕——不要試圖把 token 放在 URL 裡。命令型工作在 gateway 主機上執行，不是在沙箱裡，所以 --command 的內容應視為主機層級操作來審查。

疑難排解 — 排程沒觸發時的檢查順序

官方建議的四步檢查與六個指令
實用排錯
✅ 按這個順序查

1. 排程器狀態 — 確認 cron.enabled: true，且環境變數 OPENCLAW_SKIP_CRON 未設定。
2. gateway 是否運行 — 排程在 gateway 內執行，不在模型內；gateway 沒起來就不會跑。
3. 時區設定 — cron 排程確認 --tz 是否與主機時區相符；未指定 --tz 的 at 排程預設 UTC。
4. 執行狀態 — 跑 openclaw cron runs --id <jobId> --limit 20 查歷史；出現 reason: not-due 表示手動執行時工作尚未到期。

排錯指令組 

openclaw status
openclaw cron status
openclaw cron list --all
openclaw cron runs --id <jobId> --limit 20
openclaw logs --follow
openclaw doctor
ℹ️ 「跑了但我沒收到」與「根本沒跑」是兩種不同問題。cron runs 有紀錄 = 排程正常，問題在傳遞（回頭看第 6 節的五個原因，特別是 NO_REPLY 抑制與 --none）；cron runs 沒紀錄 = 問題在排程器、gateway 或時區。
